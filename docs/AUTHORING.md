# Authoring guide: lessons, reviews, homework, exams and drills

This is the contract between content authors and the engine. Every content file is JSON under `app/content/`. `node app/tools/validate.mjs` enforces section 7. Read `PLAN.md` sections 5, 8 and 9 for the engine side, and `design-research.md` sections 5, 8 and 9 for the pedagogy and voice this encodes.

## 1. Lesson file

`content/courses/<course>/<lesson>.json`

```json
{
  "id": "l3-shrinking",
  "course": "conditional",
  "title": "Shrinking the sample space",
  "minutes": 12,
  "objectives": ["Compute a conditional probability by counting what is left", "Explain why the condition shrinks the denominator"],
  "skills": ["cond-shrink"],
  "screens": [ ...8 to 12 screens... ],
  "summary": {
    "ideas": ["A condition throws away every outcome that contradicts it.", "...", "..."],
    "formula": { "name": "Conditional probability", "tex": "P(A \\mid B) = \\dfrac{P(A \\cap B)}{P(B)}", "note": "Count inside B, not inside everything." },
    "trap": "Adding the two chances counts the corner cell twice."
  },
  "quiz": [ ...3 to 5 items... ]
}
```

- `skills` are ids declared in the course's `course.json`. Every lesson names at least one.
- `minutes` is the planned time. `session` (optional, ENGINE-BACKLOG 556) says what kind of sitting it is: `short` (the default: the 11 to 15 minute lesson, `minutes` 5 to 20), `workshop` (`minutes` 20 to 90) or `project` (`minutes` 60 to 240). With `workshop` or `project`, `minutes` is the true estimate, with no 15 cap. The validator checks the enum and that `minutes` fits (the ranges are `SESSION_RANGE` in `app/js/hours.js`; the workshops found run 25 to 60 minutes and no project exists yet, so the ranges are the brief's, unchanged). Write `"session"` on the line after `"minutes"`. A workshop or project shows its length ("Workshop, 60 min") on the lesson start screen, the lesson's row and card on the course page, and the course card on Learn, and its weight in the topic's hours is `minutes / 14` (section 14).

### Duration in the opening prose (ENGINE-BACKLOG 557)

The validator warns `duration-prose` when the opening prose states a time that differs from `minutes` by more than 5. The one matcher is `app/tools/duration-prose.mjs` (`node app/tools/duration-prose.mjs --all` lists the hits and counts by variant).

- Where: the `prose` of the first two screens.
- What: a quantity then a unit, in five variants: `digits-min` ("60 minutes", "35 min", "45-minute"), `words-min` ("forty-five minutes"), `digits-hour` ("2 hours", "1.5 hours", "3-hour"), `half-hour` ("half an hour"), `words-hour` ("an hour", "one hour", "two hours", "a full hour").
- Ignored as data: a duration right after "every", "each" or "per" ("trades every 5 minutes"), or right before "later", "ago", "apart", "bars", "candles", "window", "interval", "sample" and the like ("10 minutes later", "5-minute bars"). Seconds are never read.
- Ignored as item times: anything under 20 minutes ("two minutes a question"). A short lesson (5 to 20 minutes) already holds it.
- The figure a lesson states is the largest that survives; the warning fires when it differs from `minutes` by more than 5.
- Known false positives: a duration that is a problem's data and not the lesson's length ("a 60-minute exam" inside a question, "a graph over 25 minutes", "an hour" as an arrival rate, "two hours free this week" in a scenario). The matcher cannot tell these from "this lesson takes about 25 minutes". Once a person has read the opening prose, add the lesson to `app/tools/duration-prose-ignore.json` with the reason; the validator then skips it. Better, write the lesson's own length in words the matcher reads and the data in a way it does not.

## 2. Screens

Every screen has `type`, and most have `canvas`, `question` and `widget`. Prose supports inline `$...$` and display `$$...$$` KaTeX, `**bold**`, `*italic*`, inline code in backticks, and fenced code blocks (```python). A fenced block shows its language and a Copy button in a strip above the code (an output block, ` ```text ` or ` ```output `, has no Copy button); long lines scroll sideways inside the block. Inline code keeps its spaces and may wrap when a line is full. Code spans are read first, so `$` and `*` inside backticks stay literal (`` `echo $HOME` ``, `` `ls *.py` ``). Display maths wider than the column scrolls sideways in its own box on a phone. Lines starting `- ` (or `* `) make a bulleted list and `1. ` a numbered one, in lesson prose and in set items alike. A Markdown table (a header row `| a | b |`, a separator `|---|---:|`, then rows) renders as a table in prose, set-item prompts and long-form model answers; `:---:` and `---:` align a column. A fenced block fits about 54 characters a line in the 540px column before it scrolls, so wrap long code by hand where the line breaks naturally. Canvas captions render the same way. Keep prose under 60 words per screen.

Any screen may also carry `tags` (a list of kebab-case family names, the first being its family) and `pace` (seconds); both are defined in section 5 and checked by the validator. A lesson screen's `tags` are not read by the Interview practice deck yet (only quiz, review and homework items are), but the pace line uses them.

The player shows Start over only where there is something to put back: a canvas-bound widget, a canvas with controls or a draggable point, or an `order`, `place`, `manipulate` or `table` widget. Choice, numeric and code screens with a static diagram have none. Start over puts the canvas back as it was first drawn (its own defaults for anything the screen did not set).

```json
{
  "type": "problem",
  "difficulty": 2,
  "title": "Optional short heading",
  "prose": "Two fair dice. You learn the first die shows a 5. $P(\\text{total} = 7)$ before and after?",
  "canvas": { "kind": "grid", "params": { ... }, "state": { ... } },
  "question": "How many outcomes are still possible?",
  "widget": { "kind": "numeric", ... },
  "hints": [
    { "rung": "nudge", "text": "Which cells disagree with what you learned?" },
    { "rung": "point", "text": "The first die is fixed.", "highlight": ["r5c1", "r5c2", "r5c3", "r5c4", "r5c5", "r5c6"] },
    { "rung": "step", "text": "Only row 5 survives: six cells. Now count the ones summing to 7 inside that row." }
  ],
  "feedback": {
    "correct": "Six cells survive, one for each second die.",
    "generic": "Not quite right. Count only the cells that agree with the first die showing 5.",
    "byKey": { "36": "You counted the whole table. The condition rules most of it out.", "r5c2": "That cell is in the row, but you shaded more than the row." }
  },
  "explain": {
    "text": "Learning the first die shows 5 keeps row 5 and nothing else. That row is the new whole. Any probability now is a count within it over 6.",
    "canvas": { "shade": { "survivors": ["r5c1","r5c2","r5c3","r5c4","r5c5","r5c6"] }, "outline": "row5" }
  }
}
```

Screen types and what they require:

| type | Purpose | Requires |
|---|---|---|
| `title` | lesson name, one framing sentence, optional canvas in a static state | `prose`; no widget |
| `explore` | free manipulation, then one observation question | `canvas` with an interactive mode (`controls`, a canvas-bound widget, points with `drag: true`, vectors in `state.drag`, or a `sim`), `widget` |
| `problem` | a graded task | `question`, `widget`, `feedback` |
| `ladder` | same canvas, one new constraint | as `problem`; reuse the previous canvas kind |
| `demonstrate` | animated step-through | `steps: [{ "caption": "...", "canvas": {state patch} }]`, 3 to 6 steps; no widget |
| `trap` | the common misconception, met and resolved | as `problem`; at least one `byKey` line naming the misconception |
| `generalise` | the rule as a description of what the learner just did | `prose` with the formula in KaTeX (in a programming course, a topic on the code track, a fenced code block stating the pattern does instead); `widget` with one confirmation item |
| `derive` | complete a missing line | `widget` of kind `expression`, `order` or `choice` |
| `transfer` | same idea in a quant context | as `problem` |
| `summary` | not a screen: the `summary` block renders after the last screen | |

Lesson shape (design-research 8.3): hook (problem or explore), explore, name (generalise comes later, but the term is introduced on this screen by what was just done), ladder 2 to 4 screens, trap, generalise and derive, transfer, then summary and quiz. Eight to twelve screens, at most one `title` and at most two non-task screens (`title`, `demonstrate`, `generalise` without a task) per lesson. Difficulty runs 1 up to 3 across the screens.

`hints`: up to three rungs in the order nudge, point, step. `point` carries `highlight` ids for the canvas. Hints are optional on `explore`, required on `problem`, `ladder`, `trap`, `transfer` and `derive`.

`feedback.byKey`: keys are the `key` values the widget can return (option ids, `wrong[]` ids, region ids, token ids, state ids). Each line names the learner's own action, never the rule. At most three sentences.

The engine's end-of-lesson order is: summary card (last progress step), quiz, celebration with the streak moment, Next or Done.

`explain.text`: at most three sentences, refers to what the learner did, with the `explain.canvas` patch showing the annotated state.

## 3. Widgets

Each `widget` has `kind` and the fields below. `label` is the accessible name of the control.

### `choice`

```json
{ "kind": "choice", "layout": "grid|stack", "options": [
  { "id": "a", "text": "$1/6$", "correct": true },
  { "id": "b", "text": "$1/36$", "why": "You kept the whole table as the denominator." },
  { "id": "c", "text": "$2/6$", "why": "You counted (5, 2) and (2, 5), but (2, 5) is gone." }
] }
```

Exactly one `correct`. Every distractor has `why` (one named misconception each). Options may be text, KaTeX, or `{ "image": "art-id" }` for a course art glyph. Options are shuffled by default, from a seed fixed for the attempt (a page visit; an exam's seed): the order is stable while the learner works, so a re-render never reorders, and changes on the next attempt. Every screen that shows a `choice` or `multi` (lesson, quiz, review, homework, exam, mock, drill and bank) takes the same path, and grading, `canvas` patches and `byKey` lines follow the option `id`, never its place. `"shuffle": false` keeps the authored order: use it when the options are ordered (ranges, steps, plain numbers in order) or refer to each other ("both of the above"). Never name an option by its place ("the first", "option B") in `explain`, `why` or feedback: the learner's order differs from yours (ENGINE-BACKLOG 591).

An option may hold a fenced code block (```` ```python ... ``` ````): it is drawn as a small multi-line code block inside the option, with no Copy button, and any text around it stays inline.

Any `choice` or `multi` option, and any `numeric`, `slider` or `tap-regions` `wrong[]` entry, may carry a `canvas` patch: it is applied by Show why after that wrong answer and reverted on Try again. Use it to show the consequence of the misconception on the diagram (highlight the double-counted cell, mark it `×2`).

### `multi`

Same as `choice`, several `correct`, shuffled by default and `"shuffle": false` to opt out, as for `choice`. The question line must say "Select all that apply".

### `numeric`

```json
{ "kind": "numeric", "answer": 0.1667, "tol": { "abs": 0.0005 }, "unit": "", "placeholder": "fraction or decimal",
  "accept": "Any form equal to 1/6, or 0.1667 ± 0.0005",
  "wrong": [ { "id": "whole", "value": 0.0278, "tol": { "abs": 0.001 } }, { "id": "double", "value": 0.3333, "tol": { "abs": 0.001 } } ] }
```

A `wrong[]` value must lie outside the answer's tolerance, and its own `tol` must not reach it (the answer is graded first, so it would be marked correct and never fire). Two `wrong[]` entries that overlap are flagged too: the first takes the key. Validator rule 581, on numeric widgets and editable table cells; it warns today and becomes an error once existing hits are fixed. `tol` is `{ "abs": x }` or `{ "rel": r }`. Integers use `{ "abs": 0 }`. `unit` may be `%`, `£`, `$`, or a word; with `%` the learner types 16.7 and the engine compares 0.167, so **the key is the fraction** (0.167, never 16.7). `accept` is shown after grading.

Validator (item 515), for `unit: "%"` on any numeric widget (lessons, quizzes, sets, exam items and parts, bank, drills) and on its `wrong` values: an error when the leading figure of `accept` (the first number, before any colon) is followed by a per cent sign and equals the key exactly, whatever the key's size and unless it is zero (at or below 1 only the answer is checked, not `wrong` values) (key 15.87 with accept "15.87%", or key 0.63 with accept "0.630%: ...", which should be 0.0063); a warning for any other key above 1, which may be a real figure over 100% (1.25 for 125%). Add `"over100": true` to the widget to silence the warning; it never silences the error. The playthrough also types the key as a learner would (answer x 100 with and without a % sign, and the per cent figure of `accept` that represents the key: the one after the last `=` or `\approx`, else any figure whose hundredth matches the key, else the leading one; skipped when `accept` starts with anything else such as "250: 1% a day"). The validator likewise compares the key with the figure after the last `=` or `\approx` when it carries a per cent sign, else the leading figure, so working may come first in `accept` ("2% / sqrt(2000) = 0.0447%" for key 0.000447) and expects every form right. Each `wrong` entry id is a `byKey` key.

### `expression`

```json
{ "kind": "expression", "answer": "\\frac{x+1}{2}", "accept": ["(x+1)/2", "x/2+1/2", "0.5x+0.5"],
  "wrong": [ { "id": "forgot-half", "tex": "x+1" } ], "keyboard": "algebra|calculus|probability" }
```

Graded by symbolic equivalence; `accept` is the fallback list of forms (plain text as a learner would type).

`"form": "expanded" | "factorised" | "simplified"` also asks for a shape, for expand and factorise tasks with free entry. Expanded: no bracketed sum left inside a product or power (`2x + 6`, not `2(x + 3)`). Factorised: a product with a bracketed sum among its factors, or a power of one (`2(x + 3)`, `(x + 1)^2`, a leading minus allowed). Simplified: like terms collected and fractions cancelled (`5x`, not `3x + 2x`). An equal answer in the wrong shape returns the key `form` (give it a `byKey` line; the default line says what to do). **Constant answers (ENGINE-BACKLOG 596).** When the answer has no free symbol (a number, a surd, a complex number), grading is by value, so retyping the prompt's unevaluated form would score. `"form": "rectangular"` asks for $a + bi$: one real part and one imaginary term (a number, a surd or a fraction times $i$), so $\frac{4+7i}{2-3i}$, $(1+i)^2$, $2(1+i)$, $\frac{1+i}{2}$ and $1 + 2 + 3i$ all return `form`, while $-1 + 2i$ and $\frac{1}{2} + \frac{\sqrt{3}}{2}i$ pass. `"form": "simplified"` on a constant also refuses what is left undone: two plain numbers added or multiplied (`2+3`), a division by a complex number, a bracket holding $i$ inside a product or power. Use `rectangular` for a complex answer and `simplified` for a real constant; both read the learner's text only, so `answer` and `accept[]` are never checked against them. Without the maths engine the text fallback accepts only `answer` and `accept[]`, so write every accepted form in the asked shape.

How equivalence is decided: when both sides evaluate to numbers, agreement at six seeded points (every free symbol from 0.3 to 3) decides, so true identities the symbolic engine misses still pass and `5R` fails for `5\sqrt{R}`. Counting answers may use `\binom{n}{k}` (also `\dbinom`, `\tbinom`, `{n \choose k}`) and factorials: both sides are then compared at whole-number points from 1 to 12 (points where either side is undefined are skipped), so `\binom{n}{2}` and `\frac{n(n-1)}{2}` agree and `\frac{n!}{(n-k)!}` can be an answer. `"upToConstant": true` accepts an answer that differs from `answer` by a constant (antiderivatives: `x^2 + C`, `x^2 + 5` and `x^2` all pass for `x^2`), so `+C`, `+c` and `+K` need not be listed in `accept`.

**Equations and inequalities in `expression` (items 618, 619).** Two relations are compared as equations, never by truth value: `answer: "y=2x+1"` accepts `2x+1=y` and `2y=4x+2` (lhs minus rhs is a nonzero constant multiple), not `y=2x+2`. For `<`, `>`, `\le`, `\ge` the direction must agree (`x<3` accepts `3>x` and `2x<6`, not `-x<-3`); `\ne` accepts any nonzero multiple; a chain such as `1<x<3` matches only the identical text; an equation never matches a non-equation, and `upToConstant` never matches a relation. When the `answer` has no `=`, a learner's `n = expr`, `expr = n`, `C = 3+2n` or `\text{cost} = 3+2n` (one letter or `\text{...}` on one side) is graded as `expr` and marked correct. List an `=` form in `answer` or `accept` only when the equation itself is the answer. `node tools/test-expr-equations.mjs --local-cdn <pkgs> [--audit]` checks this and lists authored relations.

**Left-hand labels in `expression` (item 620).** The same strip, when the `answer` has no `=`, also drops a side that is a decorated or subscripted symbol (`S_\infty`, `u_{n+1}`, `\bar{x}`, `x'`, `x_{\text{max}}`), a call of one symbol on symbols (`f(x)`, `f(k)`, `g(t)`, `f(x,y)`), or a name of two or more letters (`OB`, `TM`, `AB`) none of whose letters is a symbol of the authored answer. When neither side is a label, the input passes only if both sides are equal expressions and the right equals the answer (the learner restated the item: `(x+3)^3 = x^3+9x^2+27x+27`); a false restatement gets the generic line, not a `wrong` key. `y=5` never passes for a non-constant answer. Do not add `y = ...` or `f(x) = ...` forms to `accept`, and the question need not say "type only what comes after the = sign".

**`\exp` and letters before a bracket.** A learner's `\exp(x)`, `\exp\left(x\right)` and `\exp x` (what MathLive types for the letters "exp") grade as `e^{x}`, in both directions, in every expression item including exams, so write the authored `answer` as `e^{...}` (the validator warns on `\exp`). A single letter or Greek letter, with an optional subscript or superscript, directly before `(` is a product: `r(1-x)` equals `r-rx`, `K(v_x-v_y)` equals `Kv_x-Kv_y`, `n(r-0.5\sigma^2)T` equals `n(r-\sigma^2/2)T`. If the screen really uses a function, list its letter: `"functions": ["f"]` (letters or Greek commands such as `"\\sigma"`), and `f(x)` then stays a call. Each comparison runs in its own scope, so one parse never changes what a symbol means on a later screen. Named functions (`\sin(x)`, `\ln(x)`) are untouched.

**Whole-number symbols (`integers`).** The grader compares a learner's answer with yours at six seeded points, every symbol between 0.3 and 3, so `(-1)^k` or `\cos(k\pi)` is undefined there. Add `"integers": ["k"]` (single letters or Greek commands) and those symbols are sampled at six distinct whole numbers from 1 to 9, each symbol in its own fixed order; every other symbol keeps the 0.3 to 3 range. Then `\frac{2(1-(-1)^k)}{k\pi}`, `\frac{2-2(-1)^k}{k\pi}` and `\frac{2(1-\cos k\pi)}{k\pi}` agree (`\cos(k\pi)` carries rounding error of about 1e-16, well inside the usual relative tolerance), while `\frac{4}{k\pi}` and `\frac{2(1+(-1)^k)}{k\pi}` stay wrong. It applies to exam and bank `expression` items and to `upToConstant`. The validator errors on a malformed `integers` and warns when an `answer` or `accept` contains `(-1)^k` or `(-1)^{k+1}` and `k` is not listed.

**Capital `D` and `N` (P32-expr-D).** A capital `D` or `N` is an ordinary symbol wherever it stands, so `4Dt`, `\sqrt{2Dt}`, `tD` and `\frac{x^2}{4Dt}` are products and match `4tD`, `2D\cdot 2t` and `\sqrt{2}\sqrt{D}\sqrt{t}`. (Compute Engine reads `Dt` as its derivative operator and returns a tuple; the grader writes `\mathrm{D}` first.) Type a diffusion constant as `D` with no further care. If a screen really wants the operator reading before a letter, list `"D"` in `functions`. A derivative typed as `\frac{d}{dt}` or `\partial_t` is not touched; do not use these as answers, because the grader cannot compare them.

**Complex answers.** An `i` in the answer or in the learner's input is the imaginary unit (`\mathrm{i}` too), and the grader compares the real and the imaginary part at every seeded point, so `\frac{1}{1+i}`, `\frac{1-i}{2}` and `0.5-0.5i` agree, `3-4i` fails for `3+4i`, and `0` fails for `(1+i)^2`. Free symbols stay real: write `x + iy`, not `z` and `\bar{z}`. `\overline{...}` and `\bar{...}` are the conjugate, `|z|` the modulus, and `e^{i\theta}` equals `\cos\theta + i\sin\theta`. A real answer must not use a bare `i` as an index or variable; use `k`, `j` or `n`.

**Vectors and matrices.** One widget can take a vector: `"answer": "(2, -1, 3)"` or `\begin{pmatrix}2\\-1\\3\end{pmatrix}`. A column, a row, `(a, b, c)`, `[a, b, c]` and `\langle a, b, c\rangle` are the same vector, each entry is compared by the usual seeded-point test (symbols and complex entries are fine), and a matrix answer (`pmatrix` with rows and columns) is compared entry by entry and needs the same shape. A wrong number of entries returns the key `length` (give it a `byKey` line; the default says "Your answer has 2 components. The answer has 3 components."). `\mathbf{i}, \mathbf{j}, \mathbf{k}` notation is not read: ask for the components.

**`\min`, `\max`, `N`, `\epsilon`.** `\min(a, b)` and `\max(a, b, c)` work anywhere in an answer, also added to or multiplied by something. A capital `N` or `D` is an ordinary symbol. `\epsilon`, `\varepsilon` and ε are one symbol, so list only one form. Seeded points lie between 0.3 and 3, so a switch at 0 or below (`\max(0, x)` against `x`) cannot be told apart.

### `slider`

```json
{ "kind": "slider", "min": 0, "max": 1, "step": 0.01, "start": 0.5, "bind": "p", "unitLabel": "", "answer": 0.5, "tol": 0.02,
  "wrong": [ { "id": "too-high", "from": 0.6, "to": 1 } ] }
```

`bind` names a canvas parameter the slider drives live (the canvas redraws on every change). Without `answer` the slider is an explore control and the screen's task comes from another widget; in that case put the slider under `canvas.controls` instead (section 4). `"format": "fraction"` shows the value as a fraction in lowest terms (0.375 reads 3/8) on the thumb and the ends; `"percent"` shows 0.375 as 37.5%. A long control `label` takes at most 40% of the row, and on a phone (520 px or less) it sits above the track instead of squeezing it (ENGINE-BACKLOG 608).

### `sliders`

Two or more sliders graded together, for "find a and b that reach the target".

```json
{ "kind": "sliders", "sliders": [ { "id": "a", "bind": "a", "min": 0, "max": 5, "step": 0.1, "label": "$a$" }, { "id": "b", "bind": "b", "min": 0, "max": 5, "step": 0.1, "label": "$b$" } ],
  "answer": { "a": 2, "b": 3 }, "tol": 0.05, "wrong": [ { "id": "swapped", "check": "a > b" } ] }
```

Each slider drives the canvas as a `slider` does (`bind`). `tol` is one number or one per slider (`{ "a": 0.05, "b": 0.1 }`). Instead of `answer`, `"check": "a * b"` with `"value": 6` and `tol` accepts any pair whose expression is within `tol` of `value` (give `show: { "a": 2, "b": 3 }` for Show solution). Keys: the first `wrong[]` whose `check` holds, else the id of the first slider off its answer (`off` in the check form).

### `trade`

A market-making game over the `orderbook` canvas (ENGINE-BACKLOG 459). Each turn the learner sets a bid, an ask and a size and sends them. A seeded counterparty hits the bid, lifts the ask or stays out. Cards arrive on a schedule, a position limit applies, a live ledger shows position, cash, mark-to-market and realised P&L, and after the last turn the hidden value settles the position. Put it on a `problem`, `ladder` or `transfer` screen (or a set or exam item) with an `orderbook` canvas: the learner's quote appears in the book as "You" and the opening mark as the fair value. Without that canvas the widget still plays; the validator warns.

```json
{ "kind": "trade", "seed": 6, "turns": 8, "fair": 100, "value": 103, "tick": 0.5, "range": [94, 108], "currency": "£",
  "size": { "min": 1, "max": 3, "start": 1 }, "limit": 4, "spread": { "min": 1, "max": 4 }, "quote": { "bid": 98, "ask": 102, "size": 1 },
  "counterparty": [ { "type": "noise", "rate": 0.8, "turns": [1, 4] }, { "type": "informed", "edge": 0.5, "turns": [5, 8] } ],
  "schedule": [ { "turn": 1, "text": "The share last traded at £100." },
                { "turn": 4, "text": "A report beats forecasts. Fair is now £101.50.", "fair": 101.5 },
                { "turn": 7, "text": "The value is revealed: £103.", "reveal": true } ],
  "benchmark": 8, "maxBreaks": 0,
  "strategy": [ { "bid": 99, "ask": 101, "size": 2 }, { "bid": 99, "ask": 101, "size": 2 }, { "bid": 99, "ask": 101, "size": 2 }, { "bid": 99, "ask": 101, "size": 2 },
                { "bid": 100.5, "ask": 103.5, "size": 1 }, { "bid": 100.5, "ask": 103.5, "size": 1 }, { "bid": 100.5, "ask": 103.5, "size": 1 }, { "bid": 100.5, "ask": 103.5, "size": 1 } ] }
```

The authored sample is `content/exams/mock-trade-sample.json` (play it with `node tools/playthrough.mjs --exam mock-trade-sample`).

**Fields**
- `seed` (whole number, required), `turns` (2 to 40), `fair` (the opening mark, public), `value` (the hidden settlement value). The game is deterministic: the counterparty's random draws for turn `t` come from `seed` and `t` alone, so the same quotes meet the same counterparty every time, and the playthrough can replay `strategy`.
- `tick` (price step, default 0.5; the inputs snap to it), `range: [low, high]` (lowest and highest price, default fair plus or minus 20 ticks), `size: { min, max, start, step }` (defaults 1, 5, 1, 1), `quote: { bid, ask, size }` (the opening values; default fair minus and plus two ticks), `currency` (`"£"`), `dp` (price decimals, default from `tick`).
- `limit`: the position limit, either way. A quote whose size is more than the room left on a side (room to buy is `limit - position`, room to sell is `limit + position`) is cut back to the room and counts as a `limit` break.
- `spread: { min, max }`: the allowed width, ask minus bid. A spread outside it counts as a `spread` break (the quote still goes out). A bid at or above the ask is a `crossed` break and is rejected: nobody trades that turn.
- `counterparty`: one object or a list. Each has a `type` and an optional `turns: [first, last]` (1-based); the first entry whose `turns` contains the turn is used, else the first entry without `turns`.
  - `noise`: trades with chance `rate` (default 0.6), on a random side, for 1 to `maxSize` (default `size.max`), at your price. `reach` (default none) makes it refuse a price further than `reach` from the current mark.
  - `informed`: knows `value`. With chance `rate` (default 1) it lifts your ask when `value - ask > edge`, or hits your bid when `bid - value > edge` (`edge` default 0, a price distance; larger means it only trades on a clear mistake), for your full quoted size (or `maxSize`).
  - `scripted`: `trades: [{ act, size, price }]`, one entry per turn. `act` is `"hit"` (it sells to your bid: you buy), `"lift"` (it buys from your ask: you sell) or `"none"`. `price` is its limit: a hit happens only if your bid is at least `price`, a lift only if your ask is at most `price`. `size` defaults to 1.
- `schedule`: cards, `[{ turn, text, fair, reveal }]`. A card shows before that turn's quote. `fair` moves the mark (the ledger's mark-to-market and the book's fair value); `reveal: true` shows the hidden value (the mark becomes `value`). `text` may hold `$maths$`. The value always settles after the last turn.
- Grade: `benchmark` (final P&L at least this) or `band: [low, high]` (final P&L inside it), exactly one. `maxBreaks` (default 0) is how many rule breaks are allowed in all (one per turn and kind). Rule breaks fail the screen first, then the P&L.
- `strategy`: required, `[{ bid, ask, size }]`, one entry per turn: a run that meets the target. The test hook, Show solution and the Why? replay play it, and the validator plays it through the same game and errors if it misses the target or breaks a rule. It also warns when the opening quote left untouched for every turn already meets the target.
- `carry`: a name; see "Carried values" below.

**Keys for `feedback.byKey`:** `low` (P&L under the benchmark or band), `high` (over the band; only with `band`), `limit` (only with `limit`), `crossed`, `spread` (only with `spread`). The engine writes the per-turn lines itself ("Turn 3: you quoted £99.0 / £101.0 for 2. Your bid was hit: you bought 2 at £99.0. Position +2."), shows a warning under the inputs before a quote that would break a rule, and, when the eight turns are done, a results box: final P&L, the target, the rule breaks, and a table of every turn with the counterparty type and each trade's edge against the value (negative: made against someone who knew more). Check unlocks after the last turn; a miss under Try again starts the game afresh (same seed, same counterparty). Ledger: average-cost realised P&L, mark-to-market is cash plus position at the mark, final P&L is cash plus position at the value (the settlement is added to realised).

**Layout and keys.** Three steppers (bid, ask, size) with minus and plus buttons of 44 px, a ledger of four tiles (two by two on a narrow phone), the cards, the turn log. Arrow up and down change the focused value by one tick; Enter in a field sends the quote (it does not also press Check). Both themes use tokens only.

### Carried values (`carry`, ENGINE-BACKLOG 460)

Any widget may carry `"carry": "name"` (letters and digits). When its screen is checked or revealed, the learner's value is stored for the rest of the lesson (or set): a number for `numeric` (as typed), the `{ id: value }` map for `sliders`, and `{ pnl, position, cash, realised, mtm, breaks, turns, value }` for `trade`. A later screen reads it with `{{carry.name}}` or `{{carry.name.pnl}}` (add `|text` for a fallback: `{{carry.name|none}}`) in any string of its spec: prose, a canvas `state` or `params`, a `numeric` `answer`. A string that is only the placeholder becomes the number itself, so `"fair": "{{carry.desk.pnl}}"` is a number on the canvas and `"answer": "{{carry.desk.pnl}}"` grades what the learner earned; in running text numbers show to at most two places with a proper minus. The validator errors when a screen reads a name that no earlier screen of the lesson stores. Limits: the store lives in memory (reopening a lesson part-way forgets it and the fallback or 0 shows), is cleared when a lesson or a set starts, and an exam or homework item cannot read it because those papers draw every item at once.

### `drag-point`

```json
{ "kind": "drag-point", "points": [ { "id": "p1", "target": [2, 4], "tol": 0.3 } ],
  "wrong": [ { "id": "on-axis", "region": { "x": [1.5, 2.5], "y": [-0.3, 0.3] } } ] }
```

The canvas must list the same point ids as draggable. On a number-line or circle `target` is a bare number (the x value, or the angle; on a circle in radians a `tol` of 0.25 is about 14 degrees, so give 0.02 there); elsewhere it is `[x, y]`. `tol` is optional (default 0.25). On a plane, `tol: [dx, dy]` is a per-axis tolerance, `tolX` checks x alone, and a target `{ "on": "f", "x": 12.3 }` is the point of function `f` at that x, graded on x alone (so dragging along a steep curve is fair). Keys: the id of a `wrong[]` region that holds a point, else the id of the first point that is off target, so `byKey` may speak to a point by its id.

A whole line or level set can be the target: `{ "line": [[0, 0], [1, -2]] }` accepts any point within `tol` of that line, and `{ "expr": "2*x + y", "value": 0, "show": [1, -2] }` any point where the expression is within `tol` of `value` ("drag until the dot product is 0"). `show` is where Show solution puts the point (a line defaults to its first point; an `expr` target needs `show`). A plane point the widget names is draggable even without `drag: true` in the canvas.

### `place`

```json
{ "kind": "place", "tokens": [ { "id": "t1", "text": "$n!$" }, { "id": "t2", "text": "$(n-k)!$" } ],
  "slots": [ { "id": "num", "label": "numerator", "accepts": ["t1"] }, { "id": "den", "label": "denominator", "accepts": ["t2"] } ],
  "mode": "assign|order" }
```

`mode: "order"` uses one slot and grades the token sequence against `order: ["t1", "t2"]`.

Interchangeable tokens: with `"byText": true` tokens with the same text count as the same token (two `$x$` chips can go either way round); `"same": [["t1", "t2"]]` (or one list) names groups by id instead.

`mode: "boxes"` places the items of the screen's `boxes` canvas: the learner drags them between containers, with no tokens or slots of its own.

```json
{ "kind": "place", "mode": "boxes", "answer": { "hand": ["b2", "b3"] }, "ordered": false }
```

`answer` maps each container id that matters to the item ids it must hold (any order; `"ordered": true` for a row whose order matters); items not listed may be anywhere. Keys: the first item out of place (its item id). Instead of `answer`, `"count": { "hand": 2 }` asks only how many items a container holds (key `count-hand`), and `"free": true` accepts any arrangement once an item has moved (an explore task: it makes the canvas interactive for the explore rule).

`mode: "array"` orders the cells of the screen's `array` canvas: the learner drags cells along the row, and `answer` lists the opening cell ids in the order wanted (`["c2", "c0", "c1"]`, ids by opening index). Key: the first id out of place.

```json
{ "kind": "place", "mode": "array", "answer": ["c1", "c2", "c0"] }
```

In assign and order modes a token may carry `onPlace`, a canvas state patch applied while the token sits in a slot (or `{ "<slot id>": patch }` for one slot), over the canvas as it opened: dropping a `call` token into the position adds that leg to the payoff (`"onPlace": { "legs": { "c1": { "type": "call", "strike": 100 } } }`).

### `tap-regions`

```json
{ "kind": "tap-regions", "answer": ["r5c2", "r2c5"], "max": null,
  "wrong": [ { "id": "double", "set": ["r5c2", "r2c5", "r5c5"] } ] }
```

The canvas provides the regions (grid cells, venn regions, tree branches, area cells, table cells, boxes items, and number-line points by their point ids). The question line shows the running count. Optional: `wrong[].flash` (ids to flash on Show why), `countWord` (the noun in the count, on every canvas; default "shaded" on a grid, else "selected"), `only` (restrict tappable ids).

`only` limits what can be tapped; on a grid it takes set names as well as ids (`["col7", "row5"]`). The regions also include table rows (`tap: "rows"`), console lines (`l3`), vector arrows and points, graph edges (`tapEdges`), and whole sides of a pair (`tap: "sides"`, ids `left` and `right`).

Count mode, for "shade any 3 of the 4": give `count` instead of `answer`, and optionally `among`.

```json
{ "kind": "tap-regions", "count": 3, "among": ["c11", "c12", "c13", "c14"], "countWord": "parts" }
```

It is correct when exactly `count` regions are selected and, with `among`, every one is in `among`. The count reads "2 of 3 parts". Keys: a `wrong[]` id whose set matches, else the first selected id outside `among`, else `too-few` or `too-many`. Show solution selects the first `count` ids of `among`.

Ordered mode, for "tap the nodes in the order BFS visits them" or "tap the cells binary search reads": give `"ordered": true` with `answer` as the sequence. Each tapped object wears its number (1, 2, 3) on the canvas. It is correct when the taps match `answer` in order; keys: a `wrong[]` whose `set` matches the taps as a sequence, else the first tapped id not in `answer`, else the first missing one, else `order` (the right ids in the wrong order). Not combined with `count`.

### `order`

```json
{ "kind": "order", "lines": [ { "id": "s1", "text": "Write $P(A \\cap B) = P(A \\mid B)P(B)$" }, { "id": "s2", "text": "..." } ], "answer": ["s1", "s2", "s3"] }
```

Lines are shuffled on render. Per-line marks after grading. `"same": [["s2", "s3"]]` (or one list) makes lines interchangeable among their places, for independent steps of a derivation: any order of `s2` and `s3` in those two places is correct. `"after": { "d4": ["d2", "d3"] }` (ENGINE-BACKLOG 616) gives precedence rules instead: any order in which each named line comes after every line listed for it is correct, so two independent lemmas may come either way round and every valid proof order is marked right (a correct proof is never marked wrong). `answer` stays the model order and must satisfy the rules (the validator errors if it does not); `same` is ignored when `after` is set; the `byKey` key of a wrong order is the first line that stands before a line it must follow. `"distractors": ["d1", "d2"]` lists lines that must be left out (a flawed proof step, a wrong justification): include them in `lines`, leave them out of `answer`, and give each a `why` (shown as the feedback when the learner uses it). Each line gets a cross that moves it to a "Left out" list. Using a distractor returns its id as the `byKey` key, leaving out a line that belongs returns `left-out`, any other mistake the id of the first misplaced line as before. `same` and `distractors` combine.

### `table`

```json
{ "kind": "table", "columns": ["x", "P(X=x)"], "rows": [ ["0", { "edit": true, "answer": 0.25, "tol": { "abs": 0.001 } }], ["1", "0.5"] ] }
```

A cell whose `answer` is text (`"True"`, `"AAPL"`) is graded as text, ignoring case and spaces at the ends, with no `tol`; `accept: ["T", "yes"]` lists other spellings.

A cell may name its own wrong answers: `"wrong": [{ "id": "used-mean", "value": 0.12, "tol": { "abs": 0.005 } }, { "id": "linear", "text": "O(n)" }]`; when the first wrong cell matches one, the key is that id (a `byKey` line can name the slip). So key the slip line on the wrong id: a `byKey` key equal to that cell's own id (`r1c2`) never fires for the slip, and the validator warns `[table-slip-key]`. An answer written `O(...)` (or with `"compare": "bigO"`) is compared as big-O: the `O`, spaces, case, `*` and the log base are ignored, so `n log n`, `O(N log N)` and `O(n*log2 n)` all match `O(n log n)`, and `1` matches `O(1)`. `"deps": ["r1c2", "r2c1"]` (canvas ids) highlights those cells on the screen's canvas while the cell has focus, for filling a DP table beside its grid. A cell with `bind` writes what the learner types to the canvas as they type (`cells.r2c3` on a grid, `p.a-b` on a tree branch, `values.<category>` on bars and `points.<id>.y` on a plane, the last two as numbers).

### `manipulate`

An authored state graph. The learner taps an operation; the display animates to the next state.

```json
{ "kind": "manipulate", "start": "s0", "target": "s3",
  "states": {
    "s0": { "tex": "2x + 3 = 11", "ops": [ { "label": "Subtract 3 from both sides", "to": "s1" }, { "label": "Divide both sides by 2", "to": "s0b", "why": "Dividing now leaves a fraction on the left; clear the 3 first." } ] },
    "s0b": { "tex": "x + \\tfrac{3}{2} = \\tfrac{11}{2}", "ops": [ { "label": "Subtract 3/2 from both sides", "to": "s3" } ] },
    "s1": { "tex": "2x = 8", "ops": [ { "label": "Divide both sides by 2", "to": "s3" } ] },
    "s3": { "tex": "x = 4" }
  } }
```

Any path reaching `target` is correct. An op with `why` is a recorded misstep (its `why` is shown on the next Check if the learner has not reached the target).

An op with `"reject": true` and a `why` (and no `to`) is refused in place: the chip shakes, its `why` shows under the chips and the state does not change, so a wrong step needs no dead-end state of its own. A `manipulate` whose states carry `canvas` patches is a canvas-bound widget for the explore rule.

A state may carry a `canvas` patch: as the learner steps through states, the screen's canvas takes each patch along the path (on top of the canvas as it opened), so each algebra step can animate the drawing, such as an elimination step on a `matrix`; Undo puts it back.

### `balance`

```json
{ "kind": "balance", "left": [ { "id": "x1", "kind": "unknown", "label": "x" }, { "id": "w3", "kind": "weight", "value": 3 } ], "right": [ { "id": "w7", "kind": "weight", "value": 7 } ],
  "moves": ["remove-both", "halve-both"], "target": { "left": ["unknown"], "right": [4] } }
```

`moves` may include `remove-both`, `halve-both`, `divide-both`, `remove-unknown-both`, `subtract-both`, `add-both`, `remove-item`. Keys returned: `unbalanced`, `unsolved`.

Signed pans, for `x - 3 = 8` or `7 - 3x = 22`: a weight may have a negative `value` (drawn dashed, lifting its pan) and an unknown block may carry `"coef"` (`-1`, `0.5`, `-3`; drawn as `−x`, `½x`, `−3x`). `subtract-both` and `add-both` take any amount, `divide-both` any non-zero number (negatives too), and after each move a pan shows one unknown block (the total coefficient) and one weight block (the total). A target `"unknown"` means $1x$ alone.

Several unknown kinds: give an unknown its own `label` and a hidden `value` (`{ "id": "y1", "kind": "unknown", "label": "y", "value": 2 }`); it weighs that value, moves keep the kinds apart, `remove-unknown-both` shows one chip per label, and a target names an unknown by its label (`"left": ["unknown", "y"]` is $x + y$; `"unknown"` is always the first unknown's label).

```json
{ "kind": "balance", "left": [ { "id": "w7", "kind": "weight", "value": 7 }, { "id": "x", "kind": "unknown", "coef": -3 } ], "right": [ { "id": "w22", "kind": "weight", "value": 22 } ],
  "moves": ["subtract-both", "divide-both"], "target": { "left": ["unknown"], "right": [-5] } }
``` The `target` must be reachable from the starting pans with the listed moves (at most six): the playthrough's correct answer is the shortest such sequence, found by the engine. For `drag-point` on one-dimensional canvases (number-line, circle) `target` is a number (x or angle) and `wrong[].region` may be `{ "x": [a,b] }` or `{ "angle": [a,b] }`; default `tol` is 0.25.

### `sketch`

```json
{ "kind": "sketch", "control": 4, "target": "max(x - 100, 0)", "xRange": [80, 120], "band": 2 }
```

The learner drags control points of a curve on the `plane` canvas; graded on sampled x against the target function within `band` (y units). The control points are evenly spaced over `xRange`; Show solution (and the playthrough) puts each one on the target curve, so choose `control` and `band` so that the smooth curve through those points stays inside the band (a kink between two control points can leave it).

### `code`

```json
{ "kind": "code", "language": "python", "starter": "def max_drawdown(prices):\n    ...\n", "examples": [ { "call": "max_drawdown([100, 90, 95])", "expect": "0.1" } ],
  "tests": [ { "call": "max_drawdown([100, 90, 95])", "expect": "0.1", "compare": "isclose" } ], "how": "Submit runs 8 hidden tests. Each answer is accepted when math.isclose(actual, expected, rel_tol=1e-9)." }
```

`solution` (a full model solution, never shown before Show solution) is needed on every graded code widget (the validator warns when it is missing): the playthrough pastes it in and expects every hidden test to pass, and the starter must fail them (ENGINE-BACKLOG 343). `__learner_source__` (the learner's code as text) is always defined for `prelude` and `postlude` (not only when one is present), so a "no `sorted`" check can read it (ENGINE-BACKLOG 395, 414).

`compare` is `isclose`, `equal`, `fraction`, `stdout` or `raises` (both below). `isclose` and `equal` compare NumPy arrays, pandas Series and nested lists element by element (through `tolist()`), so `expect: "[[0.5, 1], [2, 3]]"` works for a 2 by 2 array. A NaN in `expect` matches a NaN at the same position in the actual value (a Python float, NumPy or pandas NaN, in a scalar, list, array or Series), in `isclose` and `equal`; a NaN where a number is expected, or a number where NaN is expected, still fails (item 700). A pandas DataFrame compares by `to_numpy().tolist()`, and when `expect` is a DataFrame its index and columns must match too. Dicts compare by key set (the keys must match exactly), then value by value with the same rules (tolerance, NaN, nested lists, arrays). At most 15 tests. Tests run in the Pyodide worker with a 5 s budget each; `budget` on the widget (ms) adds to a run's limit, and code that imports numpy, pandas, scipy or matplotlib gets 30 s extra without one, so the first package load is not charged against the tests. Packages load from the code's own imports, in script mode too.

`isclose` also compares complex numbers: a function may return a `complex`, a NumPy complex scalar or array, and `expect` is a Python expression such as `(0.5-0.5j)` or `[1+1j, 2-2j]`; the test is `cmath.isclose` with the same `tol` (default relative 1e-9, absolute 1e-12). A real `expect` against a complex result compares as a complex number with imaginary part 0. Without this, split the value in the call (`[w.real, w.imag]`) as before.

**Tolerance and time per case.** A case may carry `"tol": { "rel": 1e-6 }` or `{ "abs": 0.005 }` (or both, either one alone means the other is 0) for `isclose`; the row reads "Expected 10.45 (within absolute 0.005)". Use it for simulations, scikit-learn scores and tiny values (`7.6e-24` with `{ "rel": 1e-6 }`), instead of rounding in the call. Each case has its own time limit: 5 s, plus the case's own `budget` (ms), else the widget's `caseBudget`, else the widget's `budget` again (or the 30 s that heavy imports get). Loading the code has 5 s plus `budget`. A case that runs past its limit is reported on its own row ("Stopped after 5 s on this test"), and the later cases did not run, so a quadratic attempt stops after one case instead of waiting for the whole run; give a fast-path case a small `budget` and a large input to catch slow but correct code. `solution` is the code Show solution puts in the editor, which the playthrough checks against the tests; give it on every code widget.

A Python test's `setup` is read for imports as well as the learner's code (ENGINE-BACKLOG 595): if a hidden `setup` says `import pandas as pd`, pandas loads even when the learner's code imports only numpy, so no starter needs an unused import to make a data test run. Any case may carry `setup`, a line of Python run just before `call` (`{ "setup": "prices = [100, 90, 95]", "call": "max_drawdown(prices)", "expect": "0.1" }`), so the call reads cleanly. `"compare": "raises"` passes when the call raises the named exception or a subclass of it: `{ "call": "parse_price('abc')", "compare": "raises", "expect": "ValueError" }`; the result reads "raised ValueError" or "no error, the value was ...". In script mode a raises case without `call` checks the whole program (with its `stdin`). `argv: ["prices.csv", "5"]` on a case runs the program as `python3 main.py prices.csv 5` (`sys.argv`), and puts the widget in script mode.

**Hidden code around the learner's (`prelude`, `postlude`).** `prelude` is Python run in the learner's namespace before their code, and `postlude` after it; neither shows in the editor, and the learner's line numbers stay their own. Use them for helpers and data the exercise needs, or a runner that reports on the learner's tests. The learner's source is available as `__learner_source__` (a string) to the prelude, the postlude and every test call and `setup`, with or without a prelude, so a postlude can write it to a file and run a tool on it, and a test can check it directly: `{ "call": "'sorted(' not in __learner_source__", "expect": "True" }`. A postlude flag works too (`NO_SORTED = 'sorted(' not in __learner_source__`, then a case on `NO_SORTED`). There is no shared tree helper library: a lesson that needs `Node`, `build` and `to_list` defines them in its prelude. Real pytest loads in the browser: this postlude runs the learner's tests and leaves the exit code in `RESULT` (0 when every test passes):

```json
"postlude": "import pytest as _pt\nopen('test_mine.py', 'w').write(__learner_source__)\nRESULT = int(_pt.main(['-q', '-p', 'no:cacheprovider', 'test_mine.py']))\n",
"tests": [{ "call": "RESULT", "expect": "0" }]
```

To check that the learner's tests catch planted bugs, the pytest course's level 2 screens share one postlude (copy it from `pytest/l5-empty-one-many.json`) that defines `run_tests()` (runs pytest on the learner's file and prints its report: an example `{ "call": "run_tests()", "expect": "0" }`), `outcome(fn=planted)` (`"passed"`, `"failed"` or `"no tests"`, with that function swapped into the test module, output hidden), `count(test="test_x", fixture="prices")` (collected test cases, parametrised rows counted) and `is_fixture(f)`. A hidden case then reads `{ "setup": "planted = lambda prices: ...", "call": "outcome(simple_returns=planted)", "expect": "'failed'" }`. Each pytest run takes about half a second once the wheel is loaded.

In script mode both run on every case, around the program. Every run starts in a fresh, empty working directory, so files written by one run are gone in the next. `isclose` needs a real number: the text `"0.05"` fails it. In Pyodide's NumPy (2.0.2), `np.linalg.solve` and `np.linalg.inv` return `nan` for an exactly singular matrix instead of raising `LinAlgError`, so a `compare: "raises"` case cannot rely on NumPy's own singular-matrix error: have the learner's code check `np.linalg.det` and raise itself.

The first run that imports a package (numpy, pandas, pytest) fetches it once; the results panel says "Loading numpy, pandas" meanwhile, and that time does not count against the tests' limit. pytest works (`pytest.approx`, `pytest.raises`): call test functions from a `setup` line or a `call`. Python's `sqlite3` works too, but `Connection.backup()` hangs in Pyodide: copy a database with `dst.executescript("".join(src.iterdump()))` instead. If the untouched starter itself stops with an error, Check says the starter is not finished yet and folds the traceback away.

**Programs that print (script mode).** For a program rather than a function, give a case `"compare": "stdout"` and the printed text as `expect`; `stdin` (optional) feeds `input()`, one line per call:

```json
"tests": [ { "compare": "stdout", "stdin": "250\n262.5\n", "expect": "Return: 5.00%\n" },
           { "compare": "stdout", "stdin": "100\n90\n", "expect": "Return: -10.00%\n" },
           { "stdin": "200\n210\n", "call": "ret", "expect": "0.05", "compare": "isclose" },
           { "stdin": "1\n2\n", "call": "len(printed)", "expect": "1" } ]
```

As soon as any example or test is a stdout case or has `stdin`, the widget is in script mode: the learner's code runs afresh for every case (with that case's `stdin`, or none), so `input()` works and nothing leaks from one case to the next. A stdout case with `"lines": true` passes when every line of `expect` appears in the output in order (other lines, such as timings, may come between), and `"match": "took \\d+ ms"` when that regular expression is found anywhere in the output (expect may then be left out). Otherwise a stdout case compares the whole printed text, whitespace-normalised (trailing spaces on each line and blank lines at the start and end are ignored); add `"exact": true` to compare character for character. `input()` prompts are not part of the output, so `expect` holds only what `print` wrote. A `call` case in script mode is evaluated after that run, in its namespace, where `printed` is also defined: the printed lines as a list (so `len(printed)` and `printed[-1]` make good follow-up tests). When the tests run out of `stdin` lines, `input()` raises `EOFError` and the row says so. Results show the input, the expected output and what the code printed. Outside script mode, Run examples also shows anything the code printed as it loaded. Do not read the harness frame (`sys._getframe`) to get at printed output; the validator warns about it.

**Data files (`data`, ENGINE-BACKLOG 469).** `"data": { "houses.csv": "content/data/houses.csv" }` on a Python `code` widget copies each file into the working directory before every run, so the learner's code, `prelude`, `postlude`, `setup` lines and hidden `tests` all open it by its bare name (`pd.read_csv('houses.csv')`, `open('feed.hex')`). The key is the name the code sees (letters, digits, dot, dash, underscore; no folders); the value is a path under `app/content/data/` (put each course's files in a folder of its own, `content/data/<course>/<name>`). Files are text (UTF-8: csv, tsv, json, txt, hex) and at most **256 KB each**; the validator errors on a missing file, a larger one, a name or path that is not of that form, and `data` on a C++ widget (C++ has no file system: pass the data as `call` arguments, or put it in the `prelude`). Every run starts in an empty directory, so a file the code writes is gone afterwards, and a data file is fresh on each run. A `data` name may not also be a key of `files`. Under the editor a closed "Data files in the working directory" panel shows each file's size and first six lines, so the learner sees the columns without printing them; `"dataPeek": false` leaves the panel out (use it when finding the layout is the exercise). The widget works the same in a lesson screen, a quiz, review or homework item, and an exam or mock item; a drill file takes `data` too (section 5). Hidden tests in a drill are expressions, so they read a file inside the `call` (`len(open('feed.hex').read().split())`); there is no `setup`. Files are fetched once per page and cached; if one cannot be fetched the run stops with a plain sentence. Workaround before this existed: a seeded generator in `prelude`.

#### C++ (`language: "cpp"`)

With `"language": "cpp"` the learner's code is real C++17, compiled in the browser by clang 21 (YoWASP Clang, `@yowasp/clang@21.1.4-3`, with wasi-libc and libc++) and run as WebAssembly. Each Check compiles once, then runs every case as its own process, so a crash in one test does not hide the others. A starter with `#include` must say `"language": "cpp"` (the validator checks it). The same case shapes as Python apply, with these differences:

- **Function mode** (cases with `call`). `call` is a C++ expression (`"mean({1.0, 2.0, 3.0})"`), or a function name with `args`, a list of JSON values that become C++ literals: a whole number is an `int` (`long long` above 2,147,483,647), a decimal is a `double`, `true`/`false` a `bool`, text a `std::string`, and a list a braced list that converts to the parameter's `std::vector` (nested lists to `std::vector<std::vector<double>>`). Where inference is ambiguous (an overload, a template, a whole number meant as a `double`), give `types`, one per argument: `{ "call": "mean", "args": [[-5]], "types": ["std::vector<double>"], "expect": -5, "compare": "isclose" }`. Supported argument and return types: `int`, `long long`, `double`, `bool`, `std::string`, `std::vector<int>`, `std::vector<double>`, `std::vector<std::string>`, `std::vector<std::vector<double>>`, `std::vector<long long>`, `std::vector<std::vector<int>>`, `std::vector<std::vector<long long>>` (also any integer or floating type, `char`, `std::pair`, and other containers as lists). **Nested integer vectors and `long long`** (engine pass C, item 472): give `types` for an argument that is a nested list (`"types": ["std::vector<std::vector<int>>"]`), so every inner list is written as `std::vector<int>{...}`; without `types` a list of lists is a braced list, which converts to the parameter's type but fails to compile when a whole number past 2,147,483,647 sits beside smaller ones (it becomes `2147483648LL` in an `int` list), so give `types` whenever a list holds such a value. A `long long` or `std::vector<long long>` result is read back as a JSON number: compare it with `equal`, written as a plain number in `expect` (`4000000000`), exact up to 9,007,199,254,740,991 (2^53 − 1); above that write the case so the answer is smaller (a modulus, a count). A ragged or empty inner list is fine (`[[], [5], []]`). Both are covered by the drills `sample-cpp-row-sums` (nested `int` in, `std::vector<long long>` out) and `sample-cpp-merge-intervals` (nested in and out). `expect` is a JSON value, not source text: `2.5`, `true`, `"APPL"`, `[[1, 4], [2, 5]]`. `isclose` compares numbers as Python's does (relative 1e-9) and lists element by element; `equal` is exact. A `void` call returns nothing (test it through `setup` and a follow-up expression). `setup` is C++ statements run before the call, in the same scope: `{ "setup": "std::vector<double> xs(1000, 99.5);", "call": "mean(xs)", "expect": 99.5, "compare": "isclose" }`. A row shows the expression, the expected value and what came back, with its C++ type on a failure ("Expected 2.5, got 2 (int)"). A `main` the learner writes is renamed in function mode, so it never clashes with the tests.
- **Script mode** (a `stdout` case, `stdin`, `argv`, or a `raises` case without `call`): the program is compiled as it is, with its own `main`, and run once per case; `stdin` is what `std::cin` reads. `stdout` cases compare the printed text, whitespace-normalised, or character for character with `"exact": true`. A C++ script-mode case cannot also have `call` (there is no namespace to evaluate it in) or `setup`.
- **`"compare": "raises"`.** `expect` names an exception type, with or without `std::` (`"std::invalid_argument"`); a base class matches too (`"std::logic_error"`). Without `expect`, any abnormal end passes: an uncaught exception, a crash (`assert`, `abort`, a libc++ check) or a non-zero exit status (`return 1;` from `main`). A thrown exception that is not caught ends the program with g++'s message (`terminate called after throwing an instance of 'std::invalid_argument'` and `what():`).
- **`prelude` and `postlude`** are hidden C++ placed before and after the learner's code in the same file (a `struct` the exercise needs, a helper the tests call). The learner's line numbers stay their own: compiler messages name `main.cpp:LINE`, a failing test's call is reported as `test N`, and hidden code as `prelude.cpp` or `postlude.cpp`.
- **Compile errors** show clang's message under the editor (with the source line and caret), and no test runs; an untouched starter that does not compile gets the plain "not finished yet" sentence with the message folded away. Warnings about the learner's code are shown above the results when the code compiled.
- **Limits.** Compile time does not count against the tests (the results panel says "Compiling..."); each case has 5 s (`budget` adds milliseconds per case), after which the run is stopped and the remaining cases are not run, and the compiler survives. Output is cut at 200,000 characters. Flags: `-std=c++17 -O1`, libc++ in its debug hardening mode, so `v[10]` on a 3-element vector stops with "libc++ Hardening assertion ... vector[] index out of bounds" rather than reading garbage. The stack is 8 MB; an overflow or a bad pointer is reported as a crash. There is no file system, no threads and no network. Exceptions can be thrown but not caught: the sysroot's runtime has no unwinder, so a `throw` always ends the program as an uncaught exception would, and `catch` blocks never run. Do not set exercises that rely on `try`/`catch` (say so in the prose if exceptions come up). At `-O1` an endless loop with no side effects is removed by the compiler (C++ allows it), as on a desktop build. `#include <bits/stdc++.h>` does not exist (libc++, not libstdc++).
- **Tolerance, flags and variants (pass 7).** `tol: { "rel": r }` or `{ "abs": x }` on an `isclose` case, as in Python. `"flags": ["-Wall"]` on the widget adds compiler flags: `-W...` (warnings show above the results), `-O0` to `-O3` and `-Os` (replacing `-O1`), `-DNAME` or `-DNAME=v`, `-UNAME`, `-ffast-math`, `-std=c++14` or `c++20`; any flag other than a warning turns the precompiled header off, so such a Check compiles in a few seconds. A case's `"defines": { "BUGGY": 1 }` is compiled ahead of the prelude, once for every distinct set of defines, so a hidden pricer can `#ifdef BUGGY` and a learner's test is run against version A and version B.

- **Complex results.** A `std::complex<double>` (or `float`, or a vector of them) can be a function's result; write `expect` as `{ "re": 0.5, "im": -0.5 }`, or a list of those; a plain number means imaginary part 0. `isclose` compares the distance in the plane, `|actual - expected| <= max(rel * max(|actual|, |expected|), abs)` with the case's `tol` (default relative 1e-9, absolute 1e-12); `equal` compares both parts exactly. The failing row reads `(5,5)`, like `std::complex` output. With `"testkit": true`, `CHECK_CLOSE(a, b, tol)` accepts complex values too.
- **Compile checks.** A case `{ "compiles": "Connection b = a;", "setup": "Connection a;", "expect": false }` compiles that snippet in a function after the learner's code (and postlude); it passes when it does not compile (`expect: true`: when it does), and the row shows the first `error:` line. No program runs for it. Use it for a `private` member written from outside, a deleted copy, a missing `const`.
- **Checks the harness can add.** `"signature": "double total_value(const std::vector<double>&, const std::vector<double>&)"` checks the learner's function has that type (a wrong parameter type gets one plain sentence before clang's message). `"leakCheck": true` counts every `new` and `new[]`: a block never deleted, or deleted with the wrong form, ends the run with exit status 1 and a message on stderr ("Memory leak: 1 block(s) from new[] were never deleted"); allocations the compiler can see are pointless are optimised away, so test a leak that escapes (stored in a struct, returned). `"testkit": true` provides `TEST(name) { ... }`, `CHECK(cond)`, `CHECK_CLOSE(a, b, tol)`, `run_tests()` (prints `FAILED name: ...` lines and "k of n tests passed", returns the number of failing tests) and `test_count()`, so a case `{ "call": "run_tests()", "expect": 0 }` grades the learner's tests; `REQUIRE_THROWS` cannot exist without an unwinder. `"files": { "pricer.h": "...", "pricer.cpp": "..." }` adds hidden files compiled and linked with the learner's `main.cpp` (which may `#include "pricer.h"`), for a real two-file build and the linker errors that come with it; the learner still edits one file.
- **Counting allocations (`"allocCheck": true`, ENGINE-BACKLOG 470).** The harness defines `int alloc_count()` and `void reset_alloc_count()` (callable from `setup`, `call` and a hidden `prelude` or `postlude`) and replaces the global `operator new` and `operator new[]` (throwing and `std::nothrow` forms) with versions that add one to a counter and call `malloc`. `alloc_count()` returns the number of calls made by the whole program since the last `reset_alloc_count()` or start-up, including the harness's own and the test's setup, so a test calls `reset_alloc_count()` after its setup and reads `alloc_count()` last: `{ "setup": "Pool p(8); reset_alloc_count(); for (int r = 0; r < 100; ++r) { int s = p.allocate(); p.release(s); }", "call": "alloc_count()", "expect": 0, "compare": "equal" }`. `malloc` is not counted, nor are over-aligned `new` (an `alignas(64)` type) and placement new; `std::vector` and `std::string` growth are, as they call `operator new`. The counter is volatile and the unit is compiled with `-fno-builtin`, which stops clang at `-O1` from deleting a visible `new`/`delete` pair (without it `int* t = new int; delete t;` counts 0); `-O2` and `-O3` flags are safe too. It coexists with `"leakCheck": true` (one counter, one set of operators). Do not write your own `operator new`, `alloc_count` or `reset_alloc_count` in the `prelude`, `postlude` or `files`: the validator errors, and warns when `allocCheck` is on but no test reads `alloc_count()`. A starter that allocates fails the count test with "Expected 0, got 100"; say in `how` which calls are being counted. With `allocCheck` the unit is compiled without the precompiled header, so a Check takes a little longer. Engine items 518 to 520: `allocCheck` also gives `int free_count()` (calls of `delete` or `delete[]` on a non-null pointer since the last `reset_alloc_count()`, which now resets it too) and `int live_blocks()` (blocks from `new` not yet deleted, never reset), so a test can check that an assignment frees exactly the old block: `{ "setup": "Buf a(4), b(4); reset_alloc_count(); a = b;", "call": "free_count()", "expect": 1, "compare": "equal" }`. In every `allocCheck` and `leakCheck` unit, `delete` and `delete[]` now fill the block with the byte 0xDD before releasing it and keep it out of reuse until the process ends (a quarantine, capped at 64 MB, after which blocks are simply freed), so a read of freed memory returns poison (0xDDDDDDDD for an `int`, a large negative number for a `double`) deterministically and a delete-first assignment (`delete[] data_; data_ = new double[n]; copy from other`) fails for `a = a`. A second `delete` of the same block ends the run at once with exit status 1 and "Memory error: a block was deleted twice." on stderr, in both kinds of unit (with `allocCheck` alone it is reported even though leaks are not). `leakCheck`'s own bookkeeping no longer reads a freed header. Do not rely on freed memory being reusable inside such a unit.
- **Output.** A stdout case may use `lines: true` or `match` as in Python, so a program can print timings beside graded lines. When a stdout case fails, what the program wrote to stderr is folded under the row. When a case runs past its limit, what it printed so far is shown under "Printed before the error". In function mode, a `call` that indexes or reads a member of a returned temporary (`sort_book(v)[0].price`) is copied before the temporary dies, so it no longer reads freed memory.
- **Runtime notes.** A range-for over a braced list (`for (double x : {1.0, 2.0})`) needs `#include <initializer_list>` (directly or through another header) in libc++. Pointers are 4 bytes (wasm32): `sizeof(void*)` is 4 and `sizeof(std::vector<double>)` is 12, against 8 and 24 on a 64-bit desktop, and printed stack addresses are near 0x7fffe0; say so in a lesson that prints sizes or addresses. Undefined behaviour does not trap (a null read returns what is at address 0, a dangling read the stale value, a double `delete` runs on) and when clang can see it the code may compile to `unreachable` and crash, so whether it crashes depends on inlining: never use `compare: "raises"` for undefined behaviour; show sanitiser output in a `console` instead (there is no AddressSanitizer). Clocks are coarse in the browser (`steady_clock` in about 100 µs steps, `system_clock` in 1 ms steps, because the app is not cross-origin isolated), so a timing exercise batches work. A compile that fails because the precompiled header could not open a later `#include` is retried without it, so a postlude may include its own headers.
- **Hardening and what it costs (ENGINE-BACKLOG 599).** The code is compiled with libc++ hardening in the extensive mode with the enforce semantic (`-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_EXTENSIVE -D_LIBCPP_ENABLE_EXPERIMENTAL -D_LIBCPP_ASSERTION_SEMANTIC=_LIBCPP_ASSERTION_SEMANTIC_ENFORCE`), so an out-of-range `vector[]`, `string[]`, `front()` of an empty container, a bad iterator range or a null `unique_ptr` dereference stops the run with libc++'s own line ("libc++ Hardening assertion __n < size() failed: vector[] index out of bounds") and a trap. The earlier debug mode also ran libc++'s internal invariant checks, which walk a whole `std::map` or `std::set` tree on every insert and erase: 20,000 inserts and erases took 1.7 s in debug mode against 11 ms in extensive mode (the mock developer review measured 742 ms against 6 ms on one price-store workload), so a large map or set test no longer pays for them. What extensive mode does not run: the debug-only checks, such as the comparator's strict-weak-order check inside `std::sort` and `std::map` (a comparator that breaks the ordering is undefined behaviour with no message; show it with a `console` of a desk machine's output, as lesson `cpp/l22` does) and the pedantic checks of rarely misused arguments. Size a large test by native timing plus a margin; a case still has 5 s. `_LIBCPP_ENABLE_EXPERIMENTAL` only declares libc++'s experimental headers (it is how libc++ lets the semantic be set by hand); none is linked.

- **First load.** The compiler is about 26 MB over the wire (102 MB unpacked: a 73 MB `llvm.core.wasm` and a 30 MB headers-and-libraries tar) from jsDelivr, fetched once per browser cache, and takes 10 to 40 s to download and start on a fast connection; the first compile after that is slower (about 5 to 14 s) while Chrome optimises the compiler. Then a Check compiles in 2 to 5 s, and in about 1 s once the starter's `#include` lines have a precompiled header, which a second compiler builds in the background in the first half-minute on a screen. Keep the leading `#include` lines of the starter the ones the solution needs, so the precompiled header matches. Running a small program takes milliseconds.

## 4. Canvases

The binding reference for every canvas kind is the engine's own documentation: `app/js/engine/canvas/README.md` (grid, tree, venn, number-line, boxes, area, balance, circle, table) and `app/js/engine/canvas/README-B.md` (plane, bars, distribution, scatter, series, walk, matrix, vectors, complex-map, graph, array, payoff, orderbook, space, interleave). Read the entry for a kind before using it; the table below is the summary and the READMEs win where they differ. Id conventions that differ by kind: grid and area ids are one-based (`r5c1`), table and matrix ids are zero-based (`r0c0`, `A-0-1`), scatter `p{i}` and walk `path{i}` are zero-based, bins are `b{i}`, array `c{i}` uses the displayed index.

**Column width (ENGINE-BACKLOG 507).** A canvas fills the lesson column, which is 780px wide from a 768px viewport up (iPad and desktop) and the screen width less 40px below that (a 440px phone gives 400px). Design to the 540px to 780px range: an SVG canvas scales with its width, so a tall `viewBox` grows taller on an iPad (cap it with `canvas.maxHeight`), and a `table` canvas or `table` widget has up to 780px for its columns. Prose in the column stops at 70 characters a line; canvas, table, widget and code use the full width. A code editor scrolls long lines sideways inside its own box and shows a fade at the right edge while text runs on; keep authored lines under about 80 characters anyway.

`canvas: { "kind": ..., "params": {...}, "state": {...}, "enter": {...}, "controls": [...] }`. `enter` is a state patch applied 350 ms after the screen enters (use it for the "watch the space shrink" moment). Every kind also accepts `state.selected` (the current tap selection), `state.highlight` and `state.caption`. `params` fix the drawing; `state` is the initial state and the thing `explain.canvas`, `demonstrate.steps[].canvas` and `showWhy` patch. `controls` are explore-only sliders bound to params: `[{ "bind": "p", "min": 0, "max": 1, "step": 0.05, "label": "p", "start": 0.5, "format": "fraction" }]`. Where the canvas has its own binds (number-line: a point id moves that point; circle: `angle`; area: `split`, `split.rows`, `split.cols`, `grid`, `grid.rows`, `grid.cols`, `shade`) they are used; otherwise a plain `bind` sets `state.params[name]` and a dotted one such as `strike.c1` sets that state path. A control can also move one item of a list by id: `"bind": "points.p1.x"` (plane, number-line, any kind with `points`). On every kind a name the canvas does not know itself (not a number-line point, not the circle's `angle`, not an area `split`, `grid` or `shade`) is a free parameter in `state.params`, for a `derive` block to read. `start` is optional: given, it is the slider's opening value and it is applied to the canvas when the screen opens; left out, the slider opens at the bound value's current value (the point's x, the current split, the param), else at `min`. `format: "fraction"` shows the readout as a fraction (0.375 reads 3/8), `"percent"` as a percentage (37.5%); `decimals: 2` fixes the places shown whatever the step (sliders take it too). A bars canvas binds a category label to move that bar, or any other name to set `state.params[name]` for a `derive` block to read (one control driving every bar). `"scale": "log"` (with `0 < min < max`) moves the slider in powers of ten: stops at 1, 10, 100, 1000 (`perDecade: 3` adds stops between them, rounded to 3 significant figures) and the readout shows the value, not the exponent. `"stops": [1, 2, 4, 12, 52, 365]` moves a control through those values only (the readout shows the value); `"options": ["logistic", "k-NN, k = 3"]` is a categorical control, a row of chips that binds the index 0, 1, ... (put the names in the chips, not the caption); `"frames": [patch, patch, ...]` (with optional `frameLabels`) is a slider through authored state patches, each applied over the canvas as it opened (a key a frame leaves out goes back to its opening value), so "slide through the folds" is data rather than nested ternaries in `derive`. Controls work on every screen type, not only explore: on a problem, ladder or trap screen they move the canvas and grading never reads them, so a slice slider can sit beside the task on each screen of a ladder (each screen opens at its own `start`). `canvas.maxHeight: 220` (pixels, 120 or more) caps the drawing's height: it scales down, centred, so a `table` widget below a tall canvas stays in view on a laptop. Ids below are the highlightable element ids.

`derive` links values and captions to the state, re-evaluated after every patch, drag and control: `"derive": { "p2.x": "0.8 * p1.x", "caption": "Change: {{round((p1.x / 50 - 1) * 100, 1)}}%" }`. A target is an item property by id (`p2.x`), `values.<label>` on bars, `params.<name>`, `caption` or another state key; an expression uses item ids (`p1.x`), param names, top-level numbers and `values`; a string target fills each `{{expression}}`. The full function set (the same everywhere a derive runs):

| group | functions |
|---|---|
| arithmetic | `abs(v)`, `min(a, b, ...)`, `max(a, b, ...)`, `sqrt(v)`, `pow(a, b)`, `floor(v)`, `ceil(v)`, `sign(v)`, `round(v, places)` (places default 0), `hypot(a, b, ...)` |
| exponentials | `exp(v)`, `log(v)` and `ln(v)` (both natural), `log10(v)` |
| trigonometry (radians) | `sin cos tan asin acos atan`, `atan2(y, x)` |
| constants | `pi`, `e` |
| text for captions | `fixed(v, places)` ("3.50", trailing zeros kept), `money(v, symbol, places)` ("£1,234.50"; `money(v, "$")` for dollars) |
| sums and integrals | `sum(a, b, "term in k")` adds the term for whole k from a to b; `integral(a, b, "f(x)")` integrates numerically (Simpson, 400 strips); the formula is a quoted string in curve-formula syntax (`^` is a power there), and other values follow as name, value pairs: `integral(0, u, "a * x^2", "a", a)`; `fact(n)` is n! |
| tap selection | `selected` (the ids tapped so far, a list: `selected.length` counts them) and `total(selected)` (the sum of their numbers: a grid cell's shown text, a bar's height) |
| products and specials | `prod(a, b, "term in k")` (a running product), `lgamma(x)` (ln Γ), `erf(x)`, `Phi(x)` (the standard normal CDF); the same names work in curve formulas, where `prod(k, a, b, term)` is the product form of `sum` |
| matrices | `matmul(A, B)`, `matpow(P, k)` (k rounded), `vecmat(v, P)` (a row vector times P): `vecmat([1, 0], matpow(P, k))` is the chain's distribution after k steps |
| lookups | `params` (the canvas's params: `params.data[n]`) and every array in `params.params` by name (`data[n]`) |

Pass 7 adds to the function set (curve formulas too where they make sense): `erfc`, `normcdf(x, mu, sigma)` (alias `pnorm`), `normpdf` (alias `dnorm`), `qnorm(p, mu, sigma)` (aliases `PhiInv`, `NormInv`), all accurate to about 1e-14 relative (`Phi(-10)` is 7.62e-24); `solve(A, b)`, `inv(A)`, `transpose(A)`; `seq(a, b, step)`; list arithmetic `vadd`, `vsub`, `vmul`, `vscale(a, k)`, `cumsum`, `diff`, `rolling(a, w, "mean" | "sd" | "sum")`; seeded noise `randn(n, seed)` and `ar1(phi, n, seed, sigma)`; `obj("k", v, ...)` and `range(a, b)` to build an object (braces are not allowed). A single state object with an id (a plane's `area: { id: "A" }`) reads and writes by that id (`A.to`). A derive may write whole lists into state, so a series redraws from a slider (`"series.net.values": "cumsum(vsub(gross, vscale(traded, c)))"`) and a bars chart changes its categories (`"categories": "seq(0, n)"`).

`"let": { "pi": "vecmat([1, 0], matpow(P, k))" }` inside `derive` names intermediate values: they are worked out in order before the other rules, may be used by them (`"values.A": "pi[0]"`), and are never written to the state. On a `pair`, both sides' params are readable by name and the right side's win when the names clash, so give each side its own names (or read `left.a` and `right.a`). Outside quoted formulas `^` is JavaScript's bitwise XOR, not a power: write `pow(a, b)` or `a ** b` (the validator warns on `^` in a derive formula). A derive reads plain objects in state by name too (`riemann.n`, `line.m`, `transform.angle`) and an area's computed value as `values.<area id>`. Writing one component of an array keeps it an array: `"g.v.0": "a * 2"` changes the first entry of vector `g`, and `"g.v": "[a, b]"` sets the whole vector. Curve formulas (plane `expr`) may call `sum(k, 0, n, term)` for a partial sum with a slider on `n` (a Taylor polynomial) and `fact(k)`. Negative numbers, in captions and from `fixed` and `money`, print with the minus sign −. JavaScript's `(expr).toFixed(2)` and ternaries (`p1.x > 3 ? "high" : "low"`) work too; `=` and `;` are allowed only inside quoted strings (`p1.x > 3 ? "x = 3" : ""`). Details in README-B ("Linked state"). An explore screen whose only interaction is a point with `drag: true` is valid; pair it with `derive` for a live caption.

A `walk` canvas gives derive `values.stopped` (the mean of the walk at its stopping time), `values.stoppedSq`, `values.stoppedRatio`, `values.stoppedBankroll` (an overlay's mean at the stop; the name is `stopped` plus the overlay id), `values.runningMean` (list), `values.hits`, `values.hitsUp`, `values.hitsDown`, `values.tauMean` and `values.endMean` (the mean of the last step with no stopping), so a caption can read "{{fixed(values.stopped, 2)}}" beside sliders that move the barriers.

An `interleave` canvas (E13, item 471) gives derive the current shared values (`values.x`), `values.ending` (`running`, `complete`, `deadlock`, `asleep`), `values.steps`, `values.order`, and the enumeration of every legal schedule: `values.outcomes` (`{ "x=1": 18, "x=2": 2 }`, read as `values.outcomes["x=1"]`; the end states are `complete`, `deadlock` and `asleep`, or their `params.endings` names), `values.schedules`, `values.complete`, `values.deadlock`, `values.asleep` and `values.reached` (the outcomes the learner has finished at). A level author states a count such as "162 of 168" only after the canvas reproduces it: put `"state": { "outcomes": true }` on a scratch screen or read `values.outcomes` in a caption. The learner steps a lane by tapping its Step button, a lane whose next step is a lock another lane holds is disabled and drawn blocked, a schedule in which no lane can step ends "deadlock", and a `wait` with no later `notify` ends "asleep forever". `tap-regions` marks steps by id (`"answer": ["a1", "b1"]`); no widget grades the schedule itself, so ask for a count, a final value or a marked step. Worked examples (a lost update, a deadlock, an asleep-forever wait, a conditional step, an outcomes table) are in `canvas/README-B.md` under `interleave`; `content/exams/mock-interleave-sample.json` plays all five (`"sample": true`, used by no course).

Engine breadth pass 2 (grading, items 429, 430, 433, 434, 437): an `expression` answer may be complex (`i`), a vector or a matrix, and may use `\min`, `\max`, a capital `N` or `D` and `\epsilon`; `order` takes `distractors`; `isclose` compares complex numbers in Python and C++ (section 3 has each).

Plane field layers (item 431; the plane README has every option): `field: { "id": "F", "P": "-y", "Q": "x" }` draws arrows of (P(x, y), Q(x, y)) on a grid, `slopeField: { "id": "S", "f": "x - y" }` short segments of slope dy/dx = f(x, y), and `trajectory: { "id": "T", "in": "F", "from": "P" }` traces the solution through a start by fixed-step RK4. Formulas use `x`, `y` and the plane's `params`, so a slider bound to a param redraws the field. `from` is the id of a point with `drag: true` (or one a `drag-point` widget moves): the curve redraws live as it moves, and `starts: [[x, y], ...]` draws fixed curves. Options: `normalise: true` (equal arrows), `colourBy: "magnitude"` with `range`, `grid`, `back: true` (also run backwards), `length`, `step`, `by: "arc"`, `maxSteps`. Arrow counts and steps are capped, so a field costs little on a phone. `derive` can read the forward end as `values.TEndX` and `values.TEndY`. Use `equal: true` when arrow angles must be true.

Engine breadth pass 2 (walk): overlay panels under the walk (`overlays`: `"sq"` for S_n^2 - n, `"ratio"` for (q/p)^S_n, `"bankroll"` with a bet rule, or `{ id, expr }` for any formula in `n`, `S`, `x`, `p`, `q`), the running average of the stopped value across seeded paths (`showStopped`), barriers that follow sliders (`lower`, `upper`) and a mean-reverting model (`model: "ou"`, sliders on `theta`, `mu`, `sigma`).

`vectors` and a matrix (item 435): `state.matrix: [[a, b], [c, d]]` (or `state.transform`) now acts on every vector, so one matrix moves all of them with the grid and the unit square; `fixed: true` on a vector keeps it still. A `derive` reads `matrix`, `m11` to `m22`, `det`, `trace` and `image.<id>` (the arrow as drawn), and may write `"matrix": "[[a, b], [c, d]]"` from sliders bound to params `a` to `d`. Dragging a head in the image plane stores the preimage. `complex-map` (item 432) draws a z-plane beside the image of a grid under f(z); a `derive` reads `p1.u` and `p1.v`, the real and imaginary parts of f at the point `p1`.

`space` (pass 8) is the 3D canvas: drag to rotate, arrow keys turn the view, a Reset view button returns it. Formulas are written as in `plane` (`x^2 - y^2`, `cos(t)`), with the variable named for the object (`t` for a curve, `x` and `y` for `z = f(x, y)`, `u` and `v` for a parametric surface, `x`, `y`, `z` for a field) and any name from `params.params` usable everywhere, so a slider (`bind: "a"`) redraws the picture live. Coordinates in `points`, `vectors` and `planes` may be formulas too (`"v": ["a", "b", "a + b"]`). `bind: "az"`, `"el"` and `"zoom"` turn the camera. `derive` reads items by id as usual (`u.v`), `camera.az`, and `values.P` for a point's resolved `[x, y, z]` (a point `on` a surface or `at` a curve included) and `values.u` for a vector's tip. Keep the picture light: the cells of all surfaces and planes together are held near 1,600 so dragging stays smooth on a phone. Give `equal: true` when the maths needs equal units (perpendicular vectors must look perpendicular), and leave a margin round the canvas on a phone, because a finger on the picture rotates it instead of scrolling.

A ladder may move between a table and a chart of the same numbers, or into or out of a `pair`; the validator warns only on other changes of canvas kind between ladder screens.

Every canvas accepts `state.highlight: [ids]` and `state.caption: "text"`. A `derive` block also runs in the Why? copy, after `explain.canvas` is applied, so derived points and captions match the explained state. On a `pair`, `derive` reads both sides (ids directly, or `left.p1` and `right.p1`) and writes `left:` or `right:` targets: `{ "right:P.y": "sin(angle * pi / 180)" }`; controls bind `left:angle` or `right:a`. Every patch (`state`, `explain.canvas`, `demonstrate.steps[].canvas`, a wrong answer's `canvas`) may change one item of a list by id: `{ "points": { "p2": { "x": 3 } } }` merges into `p2` and keeps the rest of the list. A new id adds an item, and `null` removes one: `{ "points": { "p3": null } }` (in the Why? copy too).

Two rendering limits to write around:

- Function expressions (plane `expr`, distribution and sketch targets) read like maths: `-x^2` is $-(x^2)$, `e` is Euler's number, `e^x` and `exp(x)` agree.
- Inline maths can sit inside bold: `**the mean $\\mu$**`.
- A bare `£` inside `$...$` renders in italic maths type. Write `\\pounds` or `\\text{£}` in the JSON (both draw the pound sign in the prose face) (for example `$\\text{£}12.50$`), or keep the amount outside the maths.
- Grid cell text (`params.cells` as a 2D array) is plain text and cannot hold KaTeX. Use Unicode where you need it: superscripts such as `2³`, `x²`, the minus sign `−`, `½`.

## 5. Quiz, level review, homework, exam and drill items

An item is a `problem` screen without hints: `{ "id", "difficulty", "skills": [...], "prose", "canvas", "question", "widget", "feedback", "explain" }`. Items in the quiz block of a lesson omit `skills` (they take the lesson's).

- **Quiz** (in the lesson file): 3 to 5 items, difficulty 2 to 3, one attempt each, no canvas interaction beyond static diagrams where possible (scaffold-free).
- **Level review** `review-<n>.json`: `{ "id": "review-1", "course", "level": 1, "items": [6 to 10 items] }`, difficulty 2 to 4, interleaving every lesson of the level.
- **Homework** `homework-<n>.json`: `{ "id", "course", "level", "dueDays": 7, "items": [6 to 12] }`, difficulty 3 to 5 with at least one 5, at least one `longform` item and at least one `code` item (code courses) or one `derive`-style `order`/`expression` item (maths courses). A `code`, `order` or `expression` part of an item with `parts` counts. A `longform` item: `{ "kind": "longform", "prompt": "...", "model": "the full model answer in markdown with KaTeX", "rubric": [ { "points": 2, "text": "States the conditioning event" }, ... ] }` summing to 10. On the homework page the learner opens the model answer and the rubric with the Mark my answer button under the item; in a review, practice or redo set the Check button does it. Either way the working then locks and the learner ticks the rubric.
- **Topic exam** `exams/topic-<topic>.json`: `{ "id": "topic-1.5", "topic": "1.5", "name", "minutes": 60, "pass": 0.7, "skills": { "<skill>": "label" }, "items": [...] }`, 20 to 30 items at the 8.4 ramp (20% at 2, 50% at 3, 20% at 4, 10% at 5), every skill of the topic covered. The Learn chip shows `minutes` as written (the validator copies it into `manifest.json` `examMinutes`; ENGINE-BACKLOG 621), so set it to the time the exam really needs.
- **Stage exam** `exams/stage-<n>.json`: `{ "id": "stage-1", "stage": 1, "parts": [ { "kind": "paper", "name", "minutes", "pass", "items": [...] }, { "kind": "check", "name": "A ten-line Python script you wrote runs from the terminal" } ] }`.
- **Mock assessment** `exams/mock-<id>.json` (ENGINE-BACKLOG 453): a timed paper (or several, with self-ticked checks) that models a real online assessment or interview day. It is sat many times, so it earns no XP and keeps every attempt with a net score and a trend. It mixes topics on purpose, so the topic skill-coverage rule does not apply and `skills` on items is optional. Fields: `id` (`mock-` then kebab-case words, matching the file name), `name`, `style` (`trader`, `research`, `developer` or `strats`, which sets the colour), `models` (one plain line, up to 200 characters, saying what real test it models; shown as "Models ..." on the start card and on Review), optional `description`, optional `skills` (`{ id: name }` for the by-skill chart), and either `parts` (as a stage exam: papers and checks) or the fields of a single paper at the top level (`minutes`, `items`, and the paper fields below). Mocks are listed on Review under "Mock assessments" with the latest score, the best and a trend. Say "reported" on the intro for any format taken from candidate reports. `#exam/mock-<id>/<seed>` fixes the seed of generated items, for testing.
- **Paper fields** (on a mock paper, a stage-exam paper, or the top level of a topic exam; ENGINE-BACKLOG 450 and 451):
  - `scoring: { "right": 1, "wrong": -1, "blank": 0 }`: the marks for a right answer (above 0), a wrong one and an unanswered one (each 0 or negative). Default `1, 0, 0`. Marks may be fractions.
  - `pass` (a share of the most marks the paper can give, as before) or `passNet` (a net score, for example 55 for "80 in 8, pass on 55 net"); give one, not both. A mock paper needs one of them. `passNet` may not exceed the maximum.
  - `navigation: "forward"`: one question at a time, no navigator, no Mark, no Back, and no jumping ahead; each answer locks when the learner moves on. The default is `"free"`.
  - `skip: false`: the next question opens only once the current one is answered. With `navigation: "forward"` this is the no-return, no-skip test; with free navigation it only stops the learner moving on past an unanswered question (the validator warns). With `skip` left out on a forward paper, the button reads Skip on an unanswered question and the skipped question scores the blank mark.
  - The results page headlines the net score when any paper has wrong or blank marks (for example "6 of 14 net", "7 right, 3 wrong, 1 blank") and shows each question's marks. A paper with a short clock (under 20 minutes) turns amber for its last quarter instead of its last five minutes.
  - `required: true` on an **item** of a paper (ENGINE-BACKLOG 592): the paper fails if that item is not right, whatever the share or net score. Use it for an exit that must not be failed while the stage passes (a stage's coding task). The start card says "Must be right to pass" with the question numbers (and each paper's row in a multi-paper exam gives the count), the question carries a "Must be right to pass" tag while it is open, and the result says "A required item was wrong, which fails the paper whatever the share" with the question numbers. An item with `parts` is right only when every part is; a written item is right at the 7 of 10 rule or the rubric's pass line, and Skip marking scores it wrong. The attempt's `passedAuto` reads the same rule over the auto-marked items.
  - `tracks: ["trader", "research", "strats", "developer"]` on a **mock paper** (ENGINE-BACKLOG 593; the role ids of `prep.json`, `capstones.json` and a mock's `style`; `researcher` is read as `research`): the paper counts only for a learner whose profile track is one of them (Trader, Researcher, Strats, Developer). For anyone else, including Undecided, the paper is left out of the sitting: the start card says "Left out for your track: <paper> (<roles>). They do not count towards your pass" with a link, `#exam/<id>/all`, to sit it as well; sat that way it is optional, never gates the mock, and its result row says "Optional for your track, not counted". The route flag `as-<role>` (`#exam/<id>/as-research`, after an optional seed) sits as that role, and the playthrough sits an exam with tracked papers through `all`. A mock with a left-out paper still reads as a multi-paper mock. Tracks are for a role-specific technical prompt; a paper every path needs carries none.
  - **One-item papers** (ENGINE-BACKLOG 612): a multi-paper mock whose papers (three or more) each hold one item lists them on the start card as a compact list, "5 prompts, 11.5 minutes on the clocks" with the shared rules said once, and each paper by its minutes only. A paper whose pass mark or way of sitting differs from the rest says so on its own row.
- **Generated items** (ENGINE-BACKLOG 452): an entry in a paper's `items` of the form `{ "generator": "arith", "mix": { "add": 1, "sub": 1, "mul": 1, "div": 1 }, "n": 80, "options": 4 }` expands, when the learner begins, to `n` single-choice items, in place among any authored items. The problems come from the Today warm-up generator and `content/warmup.json` (addition and multiplication, with subtraction and division as their reverses; the same problem never follows itself). `mix` is `{ operation: weight }` (all four equally if left out); a value may be `{ "weight": 1, "a": [2, 100], "b": [2, 100] }` to narrow the ranges, which go on `add` or `mul` and apply to their reverses. `options` is 2 to 6 answers (default 4). Each wrong option is a near miss: the reverse operation, a misplaced decimal point (times or over ten) or a slipped digit. Optional `difficulty` (default 3) and `skills`. `n` is 1 to 200. The seed is chosen per attempt, so a resat differs, and is stored on the attempt (`seed`). Generated items are for mock and stage exams (not topic exams) and never join the redo queue.
- **Timed sets** (ENGINE-BACKLOG 454, covering 129): `"timed": { "seconds": 480, "lockAtZero": true }` at the top level of a level review file shows a countdown and a live "Score n of m" in the set's header; the start card states the time. With `lockAtZero: true` the set ends at zero: an answer that is ready is checked, everything else counts as missed (it joins the redo queue as any miss does) and the summary says that time ran out. Without it (the default) the clock is a guide and the learner may carry on. `seconds` is 30 to 7200. `#practice/timed/<seconds>` runs a practice set against a locking clock (the Practice card on Review links to 8 minutes). The Interview practice deck does not take `timed` yet. Timed is not for homework (the validator refuses it) or exams (a paper already has `minutes`).
- **`tags` and `pace`** (ENGINE-BACKLOG 456 and 457). Both are optional on every kind of item (quiz, review, homework, exam, mock, bank) and on lesson screens; `pace` is also allowed on a drill file.
  - `tags`: a non-empty list of kebab-case family names, for example `["dice-ev"]`. The first tag is the item's family; any others only narrow it (at most four, no duplicates). A family is a kind of question (`dice-ev`, `fermi`, `coupon-collector`), not a skill. The validator refuses a non-list, an empty list, a name that is not kebab-case and a duplicate. The engine reads `tags` for two things: the **Interview practice** deck (a tagged quiz, review or homework item of a finished lesson joins the deck under its own schedule) and the **pace line** on results (slowest families). An item with no tag counts under its first skill, and a generated arithmetic item under `mental-arithmetic`.
  - `pace`: the seconds the question should take, a positive number (a warning above 1800). Nothing is graded by it. After a set, exam or deck, the results page says how many answered items took longer than their pace, and each question shows "34 s of 45 s pace".
- **Per-item timing** (ENGINE-BACKLOG 457). Seconds per item are measured in exams (topic, stage and mock) and in every set page (practice, weekly problems, level reviews, redo and the bank deck), and the running totals are kept for exams, practice and the bank deck (not for reviews, redo or homework): from when the question is shown to when it is checked in a set, and the time a question was open in an exam (moving back and forth adds up). The results page ends its note with one line, for example "Average 46 s a question, 6 min 06 s in all. Slowest families: regime-length 3 min 20 s, coupon-collector 70 s, dice-ev 18 s. Over pace: 1 of 8 (question 2, 3 min 20 s against 45 s)." Only answered questions count. The attempt of an exam keeps `itemSeconds` (one number per question), and `ZQ.state.timing.families` keeps a running count, seconds and over-pace count per family for a later view. Marks, XP, mastery and the pass mark never depend on time.
- **Interview question bank** `bank/<family>.json` (ENGINE-BACKLOG 456): a file of interview-style items that are not tied to a lesson. `{ "id": "<file name>", "name", "description" (optional), "items": [...] }`, 1 to 200 items; split a large file by family. Each item is an ordinary item (AUTHORING format above: `id`, `difficulty` 1 to 5, `question`, `widget`, `feedback`, `explain`; `skills` optional but, if given, real skill ids; `longform` allowed, `code` not) plus:
  - `tags`: required, the family first (the file name is not read, so one file may hold several families; the real files are named `<family group>-<1..4>`, for example `bank/probability-1.json`, and are the pattern to copy).
  - `role`: required, a list from `trader`, `research`, `developer`, `strats`: the roles that ask this kind of question.
  - `style`: required, one of `mental-maths`, `probability`, `brainteaser`, `market-making`, `statistics`, `finance`, `coding`, `behavioural` (another kebab-case word is a warning).
  - `source`: required, one plain line of up to 120 characters saying where the question comes from, for example "Original" or "Adapted from mm-games review 1". Shown under the question in the results.
  - `requires`: optional list of `"course/lesson-id"`. The item is drawn only when every named lesson is finished; the validator checks that each is a lesson of that course (written or not). The Review card says how many questions are still locked.
  - `pace`: optional, as above.
  The **Interview practice** card on Review (route `#bank`) deals a deck of 8: first the items whose schedule is due (oldest first), then new ones, taking one family at a time so families mix and no two neighbours share a family when it can be avoided. Each item has its own Leitner schedule in the learner's state (`ZQ.state.bank`): a new item starts in box 1; a right answer moves it up one box (1, 3, 7, then 30 days) and it returns after that many days; a miss sends it back to box 1, due in 1 day. A bank miss does not join the redo queue, so nothing is scheduled twice. Old saves have no bank data and load unchanged. The bank is the 20 files `content/bank/<family group>-<1..4>.json` (200 items; `behavioural`, `brainteasers`, `market-making`, `mental`, `probability`). `node tools/playthrough.mjs --routes-only` checks the deck against the files, never against a fixed number: it reads every file in `content/bank`, counts the items without `requires` as drawable and the rest as locked, and expects the engine's `ZQ.select.bankStatus()`, the Review card ("N new" and the locked line) and the deck to agree, with unique uids. It then sits one deck with one item answered after 200 s and expects exactly one item over pace. `node tools/playthrough.mjs --bank <file>` (a file name without `.json`, repeatable, or `--bank all`) plays every item of one bank file: it finishes the lessons that file's `requires` name, schedules every other item 30 days out, deals decks through the real bank page, answers each item right from its key and prints pass or fail per item with a total. Use it on a new bank file before the second read. Not built: SM-2 with a self-rated ease, folding in the weekly problems, and `timed` on a deck. A bank draw for exam papers is built (section 5, Drawn items).
- **Drill** `drills/<id>.json`: `{ "id", "name", "course", "skills", "difficulty", "brief": "markdown", "starter", "examples", "tests", "how", "solution" }` (the `code` widget fields plus a model solution shown after verification). `data: { "name.csv": "content/data/..." }` (optional, Python, ENGINE-BACKLOG 469) writes those files into the working directory before the learner's code runs, as on a `code` widget (see `code`, Data files); the drill's hidden `tests` read them by bare name inside the `call`, and `dataPeek` is not used. Python drills keep the shape they always had (`fn`, `returns`, `definition`, `constraints`, `hint`, `notes`, `where`, `prelude`, tests with `call` and a Python `expect`). The drill library (engine pass C, ENGINE-BACKLOG 472, E8 with C-drill-patterns) adds these optional fields, all read from the drill file:
  - `language`: `"python"` (the default) or `"cpp"`. A C++ drill is graded by the C++ code widget, so `starter`, `examples` and `tests` follow the C++ rules of section 3 (`code`, C++ addendum): function-mode cases `{ "name", "call": "<function>", "args": [...JSON...], "types": [...], "expect": <JSON>, "compare": "equal" | "isclose", "tol", "why", "note" }`, 3 to 15 tests, at least 1 example. Nested `std::vector<std::vector<int>>` arguments and results and `long long` are supported and documented in section 3 (give `types`). The widget options `flags`, `prelude`, `postlude`, `files`, `leakCheck`, `testkit`, `signature` and `budget` are passed through. Each test runs in its own process with a 5 s limit (plus `budget`). `fn`, `returns`, and a Python `prelude` do not apply. The page shows the brief, the examples (input as the call with its JSON arguments, output as JSON), the constraints, a hint that opens after the first run, the editor with Run examples, Submit, and the model solution after a pass (or after two failed submits and a confirmation). A compile error or a missing compiler is not counted as an attempt.
  - `pattern`: one slug from the fixed vocabulary below; the `#drill` list and session setup filter on it, and the validator refuses any other value. A drill has one pattern; further labels go in `tags`.
  - `pace`: seconds the drill should take (already allowed; section 5 "tags and pace"). The stopwatch shows it and turns amber past it; it never changes the result.
  - `tags`: as elsewhere (family first). `sample`: `true` on a sample file used by no course (never listed, never drawn into a session; the validator does not ask for an `index.json` row). `difficulty` 1 to 5 as before.
  Files are flat (`drills/<id>.json`); a "pack" is a shared id prefix (`rq-`, `sy-`, `ci-`), not a folder; an optional kebab-case `pack` field names it explicitly, and `drills/<pack>` in a mock `draw` matches a drill whose `pack` is `<pack>`, whose id starts `<pack>-`, or whose id is `<pack>`. Add a row `{ "id", "name", "course", "difficulty" }` to `drills/index.json` to list a drill; the validator copies `language`, `pattern`, `pace`, `tags` and `sample` from each drill file into `manifest.json` (key `drills`), so the list filters without fetching every file. Never write them into `index.json` (the file's own value wins).
  **Pattern vocabulary** (the one list is `PATTERNS` in `js/screens/drill-lib.js`; the validator reads it from there): `hashing`, `prefix-sums`, `windows`, `stacks-queues`, `heaps-tries`, `intervals`, `bits`, `simulation` (the eight of coding-int level 4); `interpolation`, `group-regression`, `rank-one-update`, `data-cleaning` (research-int level 4); `cache`, `rate-limiter` (systems; `bits` is shared); and, for drill packs 2 to 8 of `docs/briefs/interview-plan.md`, `two-pointers`, `binary-search`, `trees`, `graphs`, `dp`, `backtracking`, `greedy`. To add a slug, add it to that array with a display name and say so in the report; do not invent one in a drill.
  **Stopwatch.** Every drill page (Python and C++) shows a count-up clock in the top bar from the moment it opens, with Pause and Restart and the `pace` beside it. Each Submit that ran tests records the reading with the result: `ZQ.state.drills.time(id, { seconds, passed, total, ok })` appends to the drill's `runs` (the last 20) in the state document, and a pass also sets `seconds` and the lowest passing time `best` (shown on the `#drill` list as "Verified · 8:12"). The pass summary says "All 9 tests passed in 8 min 12 s" and "inside the pace of 15 min" or "the pace is 15 min". Time spent on the page still counts toward build hours as before. Drills earn no XP.
  **Sessions.** `#drill/session` sets up and sits a session: two drills against one 60-minute countdown (shown in a bar with a tab for each drill, amber under 5 minutes). The learner picks pattern, difficulty range and language (the same filters as `#drill`, kept in `ZQ.store 'drill.filters'`); the engine picks two drills that match (unverified first, two patterns when it can; "Pick again" re-deals), or `#drill/session/<id>` opens a set session. **Set session** file `drills/sessions/<id>.json`: `{ "id", "name", "drills": ["<id>", "<id>"], "minutes": 60, "brief": "one sentence", "sample": true }`; `minutes` is optional (10 to 180, default 60), the two drills must exist and differ. A learner link from a lesson is `#drill/session` (any kind) or `#drill/session/<id>` (a set one). The clock is wall-clock and keeps running if the learner leaves the page; the session is kept in `ZQ.store 'drill.session'` and resumes on return. Submit always grades inside a session, even for a drill verified before. At zero (or on Finish) the session closes and a result screen gives, per drill, the time on it, the hidden tests passed (the best submit) and whether it was solved, then the total and the split ("Your split was 12 min 04 s then 31 min 40 s"). The result is kept with `ZQ.state.drills.session(...)` (`doc.drillSessions`, the last 50: `{ at, name, minutes, seconds, drills: [{ id, seconds, passed, total, ok }] }`); each drill's own record gets its runs as usual.
  **Reading a session in a lesson.** A lesson starts with the learner's latest session under the name `session`: `{{carry.session.minutes1}}` and `minutes2` (minutes on each drill, to one place), `passed1`, `total1`, `passed2`, `total2` (hidden tests), `solved` (drills passed, 0 to 2) and `minutes` (all). Use a fallback for a learner who has sat none: `{{carry.session.minutes1|none}}`. The validator does not ask an earlier widget for `carry: "session"`; no widget may use that name.
  **Checking drills.** From `app/`: `node tools/playthrough.mjs --drill <id>` (repeatable) or `--drills` opens each drill, checks that the starter (touched) fails, that the model solution passes every hidden test, that the stopwatch is read and recorded, and `--drills` and `--session` also sit the sample session (both model solutions, minutes per drill from a moved clock, the result, `carry.session`, a clock moved to zero, leaving and resuming). `--mobile` runs the same at 440 x 956 (the user's phone, iPhone 17 Pro Max), `--tablet` at 1032 x 1376 and 1376 x 1032 (iPad Pro 13-inch, both orientations), and `--narrow` at the old 390 x 844; each fails on sideways scroll. `--routes-only` checks the list filters and the session setup without running any code. Add `--local-cdn <dir>` without network access.
  **Long runs.** `node tools/playthrough.mjs --all --shard i/n` (1-based, for example `--shard 2/4`) plays every n-th item of the full ordered list (lessons, then reviews and homework, then exams), so shards 1/n to n/n cover each item once and each fits a background time limit; the routes and their checks run in shard 1 only. `--list` prints the item ids of a run without starting a browser. If Chromium closes mid-run the item is retried once on a fresh browser and the summary says `browser relaunches: R`; an ordinary failure is never retried.

### Performance task (`performance`, ENGINE-BACKLOG 529, PLAN 2c item 5)

A **performance task** is one item in a level where the learner produces what the objective names, from a blank start, graded on the product. It is the met rule's evidence that a learner can *do* the level, so it is not another quiz item. It is an ordinary item of the level's `homework-<n>.json` (or `review-<n>.json`, for the auto kinds) with one extra field:

`"performance": "code" | "derivation" | "aloud" | "data"`

Each kind is built on an existing item type; the validator checks the shape and refuses a malformed one.

| kind | built on | graded | shape the validator requires |
|---|---|---|---|
| `code` | a `code` item (Python or C++) | `auto` | a `code` widget with `tests` (3 or more cases) and strictly more tests than `examples`, so some are unseen; a `solution`; a `starter` that is a stub, not an answer (the playthrough proves it fails); no `parts` |
| `derivation` | a `longform` with an empty box | `self` (or `external`) | `longform` with no `starter`, `steps`, `order` or `derive` field, no `hints`, no `parts`, a `model` (shown only after the learner marks) and a `rubric` of 3 or more criteria summing to 10 |
| `aloud` | a timed `longform` spoken answer | `self` (or `external`) | `longform` with `seconds` (15 to 1800, the time to speak; optional `think`, seconds of thinking time that run first and then start the answer clock by themselves, and `lockAtZero: true`, which stops the answer clock at 0:00; ENGINE-BACKLOG 613) and `followUps` (1 to 5 strings the interviewer asks next), plus `model` and a `rubric` of 3 or more criteria; no `starter`, `steps`, `order`, `derive`, `hints` or `parts` |
| `data` | a `numeric` or `longform` item that reads a data file | `auto` if `numeric`, else `self` | the widget carries `data: { "name.csv": "content/data/..." }` (as a Python `code` widget does, checked the same way); a `numeric` widget needs its `answer` and `tol`; a `longform` widget has `model` and `rubric` |

Rules:
- **Where.** Homework or level review only. A `longform` item is allowed in homework only (existing rule), so `derivation`, `aloud` and a longform `data` task live in homework; `code` and numeric `data` may be in either. Not in a quiz, exam, mock, bank or drill.
- **At most one** performance task per level (across its review and homework). More than one is an error.
- **Which levels need one (the verb rule).** A level is rule-matched when any objective in its lesson files (the `objectives` of the lesson JSON, not `course.json` `lessonObjectives`) starts with write, derive, prove, build, code, implement or design; or with explain, defend or justify when the course is in Stage 2 or 3 or is an interview course (recruiting, brainteasers, puzzles, mm-games, mental-pressure, game-theory, coding-int, research-int, systems, ito, measure-prob, pdes). Stage 0 is excluded except first-python and terminal. Only a *written* level counts (every lesson, the review and the homework exist). A rule-matched level without a performance task is a validator **error**. A level that does not match may still carry one; it is then required for met in the same way.
- **Choose the kind that matches the verb.** Write, code, build, implement: `code`. Derive, prove: `derivation`. Explain, defend, justify: `aloud` (or `derivation` where the answer is written maths). Design: `code` where it runs, else `aloud`. Anything read from data: `data`. Do not add longform boxes to a level the rule does not match.
- **Grandfathering (`app/tools/perf-pending.json`).** Levels that matched the rule when item 529 landed and had no task are listed there as `course/L<n>`. For them the validator gives one warning count line instead of an error. Content agents never edit the list. A level on the list that has gained a task warns "remove from perf-pending"; the main session prunes with `node tools/perf-pending.mjs --prune` (`--write` regenerates it from scratch). A **new** level is never on the list, so it errors until it carries a task.
- **Grading.** `code` and numeric `data` are `auto`. The self kinds are marked by the learner against the rubric (7 of 10 or more is a pass, the existing longform rule); the row is stored `how: self`. `external` is reserved for a reviewer-entered mark (PLAN 2c item 8) and counts like `auto` when a producer exists.
- **Homework page (ENGINE-BACKLOG 530 to 545).** An `aloud` item (any longform with `seconds`) can be marked with an empty notes box: its label reads "Your notes (optional)" and Mark my answer does not need text. An ordinary longform still refuses an empty box. A performance item carries a "Performance task, needed for the level" tag in its header and the overview list, a line on the start card, and "Performance task passed" or "not passed" in its result row. A longform rubric row may carry `"required": true`: the self-mark fails if that row is not ticked, whatever the total (a warning fires when every row is required; `required` must be a boolean). A homework item `title` is plain text: a `$` in it raises a warning, so write the title in words. `playthrough.mjs --set` plays the starter of every `performance: "code"` item (it must fail), marks each longform item through the real Mark my answer button (an empty box refused unless aloud), shoots it as `-marked` with `--shots`, and checks `state.perf` after a homework holding a performance item.
- **Which ticks pass (ENGINE-BACKLOG 698).** From `app/`, `node tools/rubric-passes.mjs --item content/courses/<course>/homework-<n>.json#<item-id>` (or `--course <course>`, or `--all`; `--json` for data) lists every tick set of a self-marked rubric that passes (7 points or more, every `required` row ticked), the minimal passing sets, and for each row whether a pass can leave it out. Run it on a performance rubric before handing the level on: a row that names a part of the task should read "can be left out: no", by points or by `required: true`. It is advisory and always exits 0; its test is `node tools/test-rubric-passes.mjs` (fixtures in `tools/fixtures/rubric-passes/`).
- **Performance reports (ENGINE-BACKLOG 699).** From `app/`, after `node tools/validate.mjs` has rewritten `content/manifest.json`, `node tools/perf-reports.mjs` reads every level in its `perf` map and checks `../docs/reports/<course>-<n>-perf.md` for the item id, the kind, a line naming the matched objective (the word "objective" with a quoted or named lesson objective), a line starting "Overlapping screens" (heading or bold lead; names screens, or says "none"), and a mention of each of the four gates (validator, voice, numbers script, playthrough). It prints `<report>: missing <part>` per gap, lists levels with a task but no report, and exits 1 on any gap (`--warn` exits 0). Run it before handing a performance level on; its test is `node tools/test-perf-reports.mjs` (fixtures in `tools/fixtures/perf-reports/`).
- **Met, and which tasks gate (ENGINE-BACKLOG 549).** A level with a performance task is met only when the task is also passed (section 11), but only if the level is rule-matched. The validator writes `"gates": true` on that level's row in `content/manifest.json` `perf`, and `ZQ.prereq.perfNeeded` reads it: that flag is the one source. A task on a level the verb rule does not match is **practice only**. It still records `state.perf`, still shows on the homework page ("Performance task, practice only"), and never gates met, so no learner waits on a self mark for it. Passing a self-marked task never meets a level alone.

**Exam freshness (ENGINE-BACKLOG 588, 600).** An exam, drill or bank item must not repeat a setup from a lesson screen, quiz, review, homework item or another exam, even with the constants changed, and a code task must not reuse a lesson's function. Before handing an exam over, run `node tools/fresh-check.mjs --exam <id>` from `app/` (`--drill <id>`, `--bank <file>`, `--all-exams`; `--json` lists the hits). It exits 1 on any hit, naming both paths and what is shared. A course review or homework set is checked the same way with `--file content/courses/<course>/review-1.json` (a file inside `content/` keeps its own path, is never compared with itself and has its code items read from where it lives; item 604). Test: `tools/test-fresh-check.mjs`. Two checks run:

- Prose. It compares prose, question and widget prompt text. A maths span, a LaTeX command and a number each become one placeholder (`#`), so only words count. The AUTHORING instruction sentences ("Put the steps in order.", "Leave out the two that do not belong.", "Select all that apply.", "Give four decimal places.", "Say the reasoning aloud first.") are cut out and break a run; the list is `STOPLIST` at the top of the tool. **The gate:** a hit is a shared run of at least 12 word tokens (`--min-run`, default 12) that covers at least 60% of the item's words (`--min-share`, default 0.6), or a 5-word shingle Jaccard of at least 0.5 (`--threshold`). For triage a reader may loosen it with `--min-run 8 --min-share 0`, and then judges each hit. Calibration: the six session U topic exams (0.6, 1.10, 1.11, 2.5, 2.6, 3.4) all pass the gate with no hits; at `--min-run 8 --min-share 0` they give 3 to 10 hits each, all definitions or stock questions ("is compact exactly when it is closed and bounded").
- Code names. For a code widget (or a drill) the function and class names in `starter`, `solution` and the head of each test `call` are compared with every code widget in every lesson, review and homework. A shared name is a hit (`code names walk_forward_mse <- courses/validation/l6-walking-forward.json:...`), because the same task renamed in prose is a reused exercise. Ignored: names under six characters without an underscore, names starting with `_` or `test_`, a list of generic names (`main`, `solve`, `mean`, `fit`, `swap`), and a name used in three or more courses (a shared helper such as `daily_returns` or `run_tests`; `--idiom n`). `--no-code` turns it off. Catches the stage-2 reuse of `walk_forward_mse`, `irls_logistic` and `metropolis`.

Versions of one mock (`versionOf`) are not compared with each other. Read each hit and either rewrite the item or say in the report why the overlap is only stock phrasing or a deliberate shared helper. This replaces the per-exam `fresh.py` checks for setups, which compared keyed numbers only; the number checks stay.

### Follow-up parts (`parts`, ENGINE-BACKLOG 467)

An interviewer asks a question, then follows up on the answer. `parts` models that on a review, homework, exam, mock or bank item (never a quiz item: a quiz item is one question with one attempt). The item keeps its own `id`, `difficulty`, `skills`, `tags` and `pace`, and may carry a `title`, `prose`, `canvas` and `question` as the stem shown above the parts. It has no `widget` and no `feedback` of its own: each part has them.

```json
{ "id": "h-calendar", "difficulty": 4, "skills": ["ci-design"], "tags": ["calendar"], "prose": "A booking calendar takes 1,000 bookings, one at a time.",
  "parts": [
    { "question": "How many comparisons does a full scan make in all?", "widget": { "kind": "numeric", "answer": 499500, "tol": { "abs": 0 } },
      "feedback": { "correct": "0 + 1 + ... + 999 is 499,500.", "generic": "Sum the scan length of each booking." }, "explain": { "text": "..." } },
    { "question": "What do you change for a thousand bookings a second?", "widget": { "kind": "choice", "options": [ ... ] }, "feedback": { ... } },
    { "question": "Write the check.", "widget": { "kind": "code", "language": "python", "starter": "...", "tests": [ ... ], "solution": "..." }, "feedback": { ... } } ] }
```

- **Parts.** 2 to 6. Each is `{ "question", "widget", "feedback", "explain"?, "prose"?, "canvas"?, "difficulty"?, "id"? }`; nothing else (`id` is accepted, kebab-case, and has no effect: the engine names a part `<item id>-p<k>`). A part has its own `question` and its own `canvas` (a canvas-bound widget such as `tap-regions` works in a part), and `explain` falls back to the item's. Any widget kind is allowed, and kinds may differ from part to part (`numeric`, `choice`, `multi`, `table`, `order`, `code`, and so on), except `longform` (the learner marks a written answer, which a follow-up cannot wait for). Put a written follow-up in its own homework item.
- **Opening.** Part 1 is open. Part k + 1 opens once part k is checked, right or wrong: a wrong part never blocks the next. In a set (level review, practice, redo, bank deck) Check grades the open part, its own feedback shows, and Continue opens the next part; "Question 2 of 8 · Part 2 of 3" shows where the learner is. In homework and exams nothing is marked until submit, so each open part but the last has a Next part button (enabled once it has an answer) that locks that answer and opens the next. A homework draft keeps how many parts are open.
- **Credit.** Every part is worth the same. An item's credit is the number of parts right divided by the number of parts; an item counts as right (mastery, XP, the redo queue, "n of m right") only when every part is right, and a miss on any part sends the item to the redo queue once, as any miss does. In homework an item with parts earns its credit times its marks (2 of 3 parts on a 3-mark item is 2 marks). In an exam or mock the item scores `credit * right + (1 - credit) * wrong` (a part not right takes the wrong mark; with the default 1, 0, 0 that is plain credit; with negative marking, an item left at part 1 scores its unopened parts at the wrong mark, where a whole item left blank scores the blank mark), and the result shows "2 of 3 parts". A set's summary says "Counting each part of a multi-part problem: 6.3 of 8" beside the right count.
- **Written parts (ENGINE-BACKLOG 598).** A `longform` part scores its rubric ticks over its rubric points (8 of 10 ticked is 0.8 of the part), not the 7 of 10 rule that makes a written answer right or wrong on its own: the item's credit is the sum of its parts' credit over the number of parts, so a choice part right and a written part marked 8 of 10 is 0.9. The item still counts as right for mastery, XP and the redo queue only when every part is right (a written part right at 7 or more), and a required item (`required: true`) is met only then. In homework the item earns that credit times its marks, and a timed review's "counting each part" total reads it too.
- **Never opened.** A part the learner never reached counts as missed. In a `timed` review that locks at zero, the part that is open and has an answer is checked, the rest (opened or not) are missed, and the item's credit is the parts right. In an exam or homework, an item left at part 1 scores one part and the other parts are shown, locked, on the result page.
- **Code parts.** A part may be a `code` widget (Python or C++). Its hidden tests are cumulative: the tests of every earlier `code` part of the same language run first, then the part's own, repeated tests dropped, so a later part still has to pass what the earlier ones asked for. The merged list is held to 15 tests; each widget still needs its own 3 or more tests. Write each part's `tests` as only what the part adds. `"cumulative": false` on a code widget keeps its own tests only (use it when a later part changes an earlier behaviour), and it also starts a fresh merge: a later cumulative part runs the tests from that part on, not those before it. Only the `tests` merge: a test that relies on an earlier part's `setup`, `prelude`, `postlude`, `files` or `data` runs under the later part's widget, so each code part carries those fields itself. A later code part's `starter` may show the earlier part's reference solution, so each part stands alone; each part has its own `solution` for the test hook.
- **Where.** Practice sets leave out an item with a `code` or `longform` part, as they leave out those items. The old stage-exam `parts` array (papers and checks, on the exam document) is a different field on a different level; an item part with `kind: "paper"` or `"check"` is refused.

### Drawn items (`draw`, ENGINE-BACKLOG 468)

A mock resat repeats itself when its `items` are fixed. A paper of a **mock or stage exam** (not a topic exam) can say `draw` as well as, or instead of, `items`:

```json
{ "kind": "paper", "id": "oa", "name": "Online assessment", "minutes": 60, "pass": 0.6, "items": [],
  "draw": [ { "from": "bank/research-1", "tags": ["two-regressions", "special-eigenvalues"], "difficulty": [2, 4], "n": 3 },
            { "from": "drills/arrays", "tags": ["hashing"], "difficulty": [3, 4], "n": 2 } ] }
```

- **Entry.** `from` (required), `tags` (optional, kebab-case), `difficulty` (optional: one number, or `[low, high]`, each 1 to 5) and `n` (1 to 40). Nothing else. `items` may be an empty list when `draw` gives the paper its questions; drawn items follow the paper's own `items`, entry by entry, in the order drawn.
- **Sources.** `bank/<file>` is a bank file (`bank/research-1`); `bank/<prefix>` is every file named `<prefix>-1`, `<prefix>-2` and so on (`bank/research`); `bank/*` is all of them. `drills/<pack>` is every drill file whose `pack` field is `<pack>`, whose id starts `<pack>-` (the id-prefix convention: `ci-`, `rq-`, `sy-`), or whose id is `<pack>` (so one drill can be named); `drills/*` is all of them. A bank item's `requires` is ignored: a mock stands alone. A drill becomes a `code` item: its `brief` is the prose, its name the question, and its `starter`, `examples`, `tests`, `how`, `solution`, `budget` and the other code fields are the widget (a Python drill's `prelude`, which runs after the learner's code, becomes the widget's `postlude`). Its `tags`, then its `pattern` (if not already a tag), are the item's tags (a drill with neither takes `pack`, else `id`), so a draw can filter by pattern and the family is still the drill's first tag. A drawn drill is graded by the `code` widget (its `isclose` and `equal` comparisons), not the drill page's harness, so the drill page's stricter typed-result check (for example a `Fraction` for `compare: "fraction"`) does not apply in an exam: write the hidden tests so a wrong type fails there too.
- **Filters.** An item matches when it holds any of `tags` (all items match if `tags` is left out) and its `difficulty` lies in the range.
- **Fresh, unseen first and balanced.** The draw is made when the attempt begins, from the attempt's seed (`#exam/<id>/<seed>` fixes it, as for generated items, for a learner with no earlier attempt of this exam: after an attempt the same seed draws different items). **Seen** (ENGINE-BACKLOG 546) means a drill the learner has verified in the drill library (`state.drills[id].verified`), or an item drawn in an earlier attempt of this exam. The draw takes never-seen items first, from the whole pool whatever the family; only when none is left does it take seen ones, the least recently seen first (a library solve counts as older than any sitting, and an earlier sitting as older than a later one). Inside each of those tiers it is balanced across families: the families (an item's first tag) are taken in seeded order, one item from each in turn, until `n`. No item is drawn twice in one attempt, across all the entries of the exam (entries whose pools overlap share the items, so the validator refuses entries whose `n` sum to more than the items their pools hold between them), and if fewer than `n` are left the paper gets the ones that are. The attempt keeps `seed` and `drawn` (the uids, `bank/<file>/<id>` or `drills/<id>`), which is what "seen" reads, so old saves load unchanged.
- **Previously seen label (ENGINE-BACKLOG 546).** A drawn item that is seen shows "Previously seen: solved in the drill library" or "Previously seen: sat on <date>" beside its question number on the paper and in the review list of the result; the start card counts them. The attempt stores `seen` (`{ uid: { why: "solved" | "sat", at } }`, only for seen items), computed before the draw, so results stay honest after the library state changes. The library stays open: the pool is not hidden, and a learner who has worked it simply gets the label. Add enough drills that a repeated sitting still finds unseen ones; with the pool used up the draw repeats and says so.
- **Seen in any exam (ENGINE-BACKLOG 594).** A drawn item sat in any other exam, topic, stage or mock, also counts as seen (its attempt's `drawn` list), so stage 3 paper D, stage 1 paper D and `mock-oa-code` no longer draw the same small pool afresh each time. Ranking inside the unseen-first rule: a drill solved in the library ranks 0.5, one sat in another exam 0.75, one sat in this exam its attempt number. A sitting of this exam wins over another exam's, and the label reads "Previously seen: sat in another exam".
- **Marking.** A drawn item is an ordinary item of the paper: it counts for the paper's marks and pass mark (`passNet` may not exceed the most the paper can give, drawn items included), appears on the result page with its explanation, and carries its own `pace`. A drawn item is never added to the redo queue (it is not in the exam file); a bank item has its own schedule in the bank deck. Authors should give each draw at least twice `n` matching items; the validator warns below that.
- **Code.** Bank items refuse `code`, so coding tasks are drawn from `drills/<pack>`; a paper that holds only drawn drills is a coding assessment with fresh problems per attempt.

### Mock versions (`versionOf`, ENGINE-BACKLOG 547, PLAN 2c item 6)

A mock whose papers are fixed (not drawn) can ship further fixed versions as separate files, named `<base>-<n>` from 2 (`mock-oa-sig`, `mock-oa-sig-2`, `mock-oa-sig-3`). Each version file says `"versionOf": "<base>"` after its `id`; the base file is version 1 and carries no field. `prep.json` and `readiness.md` name only the base. The Prepare for page groups the files under the base mock as "Version 1, 2, 3" (a link each, "(sat)" on those with an attempt) and its button offers the next unsat version, else the one sat longest ago. The Review list shows every version as its own mock.

Validator errors: `versionOf` that names no mock, whose id does not read `<versionOf>-<n>`, or whose number is below 2; a mock named `<base>-<n>` where `<base>` exists but `versionOf` is missing; and a version whose base no prep path names, since the Prepare page would never offer it. A mock whose pool is drawn (section above) needs no versions.

### Mock pass marks

A mock's `pass` is the author's line, not a published cut-off. Where the mark comes from the course's own exit criterion (for example `mock-oa-code`, both problems in 60 minutes, `pass: 1`), the description says so and calls it illustrative: firms do not publish cut-offs.

### Samples (`"sample": true`)

An engine sample is a lesson, review, homework, exam, mock, bank or drill file that exists to exercise the engine, not to teach. A top-level `"sample": true` hides it: the validator lists it under `samples` in `content/manifest.json`, and the app leaves it out of the mock list, the bank deck and its counts, the drill list, Review, You and Prepare. It still opens by its route (`#exam/mock-sample`, `#review/<course>/<id>`), loads by id, and the playthrough plays it. A sample review or homework may sit in a course folder without being on the course map (a file on the map may not be a sample); a sample drill need not be in `drills/index.json`. A sample exam may draw from sample bank and drill files; any other exam draws from real files only. The field is `true` or absent. The engine samples are `exams/mock-sample.json`, `mock-trade-sample.json`, `mock-sample-parts.json`, `mock-sample-draw.json`, `mock-sample-data.json`, `mock-interleave-sample.json`, `bank/sample-draw.json`, `drills/sample-*.json`, `drills/sessions/sample-session.json`, `data/sample-prices.csv` (a data file, not a content file: it carries no flag) and `courses/py-found/review-sample-parts.json` and `homework-sample-parts.json`. A real drill session may not name a sample drill (the drill list hides it); mark the session a sample too.

## 6. Voice and teaching rules

From `design-research.md` 9, binding:

- British English. No exclamation marks. No emoji. Sentences aim for at most 20 words; this is a target, not a gate. Never shorten a sentence where that would weaken the teaching. The gate is 35 words (`voice-scan.py 35` reports 0); `O2-long-sentence` stays an advisory warning for readers.
- Second person for instructions, "we" for reasoning together.
- Puzzle first. Never state a rule before the learner has used it. Name a term only after it has been used.
- Derive rather than state. Every derivation line carries its justification. No "it can be shown".
- Every lesson has one trap (a `trap` screen) and one edge case somewhere in the ladder or quiz.
- Every distractor encodes one named misconception and its `why` names the learner's action.
- Explanations refer to the learner's action, three sentences at most, with a diagram state.
- Notation: random variables capitals, realisations lower case, vectors bold lower case, matrices bold capitals, `P(\cdot)`, `E[\cdot]`, `Var(\cdot)`, `\ln`, decimals in maths and percentages in prose only. Money is £ or $ consistently within a course.
- Transfer screens use real quant contexts: a bet, a price path, a portfolio, an order book, a dataset, a backtest, a signal.
- Honest about difficulty. Never praise the question. Never praise the learner beyond the sourced lines ("That's it.", "Correct.").
- Concreteness fades: the canvas is interactive early, static by the ladder's end, absent in the quiz where possible.
- Code lessons: explanations annotate only non-obvious lines; show the failing version beside the fix when the lesson is about a pitfall.

Sizing: a course has 3 to 5 levels of 4 to 6 lessons. Each level ends with a review and a homework. Size a course by its topic hours: about 60 h of topic per 12 lessons, within 12 to 30 lessons per course.

## 7. Validation rules (enforced by `tools/validate.mjs`)

Errors:

1. JSON parses; required fields present; ids kebab-case; lesson `id` matches the filename; `course` matches the folder.
2. Screens 8 to 12; at most one `title`; at most two non-task screens; `summary.ideas` has exactly 3; `quiz` has 3 to 5 items.
3. Every `problem`, `ladder`, `trap`, `transfer`, `derive` screen has `question`, `widget`, `feedback.correct`, `feedback.generic` and 1 to 3 hints in rung order.
4. Widget kinds and canvas kinds are known; required widget fields exist; `choice` has exactly one correct and every distractor has `why`; `multi` has at least one correct; `numeric` has a numeric `answer` and `tol`; `tap-regions` has `answer`, or `count` (a whole number no larger than `among`), and its `answer` and `among` ids exist in the canvas (for `grid`, `venn`, `area` with `c{i}{j}` or `c{i}-{j}` from 10 up, `table`, and `number-line` point ids); `drag-point` targets are `[x, y]`, a bare number on a number-line or circle, or `{ "on": f, "x": n }` naming a function of its plane, and `tol` is a number or `[dx, dy]`; a `pair` has a `left` and a `right` canvas, each checked as its own kind, and its ids carry `left:` or `right:`; list fields (`options`, `among`, `tokens`, `slots`, `lines`, `points`, `wrong`, `hints[].highlight` and list answers) are lists, and a field of the wrong shape is one error, never a crash; `expression` `form` is `expanded`, `factorised` or `simplified`; `place` in `boxes` mode names containers and items on its boxes canvas; `balance` `moves` are known and the `target` is reachable with them (the engine's own solver); `order` answer is a permutation of line ids; `place` slots accept known tokens; `manipulate` target is reachable from start; `code` has at least 3 tests, each a `call` with `expect` or a `compare: "stdout"` case whose `expect` is a string (`stdin` a string, `exact` a boolean, `argv` a list of strings), a `raises` case names an exception, `setup` is a string, and `printed` is used only in script mode. Canvas options checked too: a control's `scale` is `"log"` with `0 < min < max`; `canvas.maxHeight` is a number of 120 or more; series `hlines` is a list of `{ y }`; tree `state.branching` is a number, a list or an object; `sliders` has at least two sliders and an `answer` or a `check`; `order` `same` names real line ids; a `drag-point` `expr` target has `show`. `trade` (item 459): whole `seed` and `turns`, numeric `fair` and `value`, a counterparty (or list) of known type with its own fields (`scripted` has `trades`), cards inside the turns, exactly one of `benchmark` and `band`, and a `strategy` of one entry per turn that, played through the widget's own game, meets the target with no rule breaks (a warning when doing nothing already meets it); a `{{carry.name}}` reference needs an earlier screen with that `carry` (item 460).
5. ## 9. Course strand: Pure maths and Quant

The maths breadth courses are tagged so the learner can tell what is needed to be hired from what is for the love of the subject. Two optional top-level fields in a course's `course.json`:

```json
"strand": "pure",
"strandNote": "Not needed to be hired. Research roles that hire maths PhDs, and reading proofs in papers."
```

- `strand` is `"quant"` or `"pure"`. Any other value is a validator error. A course with no `strand` is untagged and shows no badge (every course written before the breadth pass).
- `strandNote` names the roles in one or two plain sentences. It is required when `strand` is set, and an error without `strand`. It is the badge's detail: the tooltip, and the screen-reader text after the strand name.
- The app shows a "Pure maths" (violet) or "Quant" (amber) badge on the course card, the course page, the lesson start screen, and on a topic's chip row and topic exam chip (Learn and the exam list on Review). A topic or exam chip gets a badge only when every course in the topic carries the same strand; a mixed or partly untagged topic shows none.
- Topic targets: a topic's `exit` in `curriculum.json` shows as a "Target" line under the topic heading on Learn. A topic with no exam file in `content/exams/` shows "Topic exam, not written yet" (Learn and Review) instead of a button. A course with no written lessons opens its map as "Map only".
- Setting: You, Settings, Study plan, "Quant path only" (`settings.quantOnly`, saved with the other settings, off by default). When on, `ZQ.content.stages()` and `courses()` leave out pure courses and any topic whose courses are all pure, so Learn, Today, Review, the mastery map and the stage progress count ("n of m topics passed") skip them. `topic()`, `course()` and `stage()` still find everything, so a link, resume point or exam URL to a pure course keeps working. Stage hours still show the full curriculum figure. `ZQ.content.allStages()` and `allCourses()` ignore the setting.
- Passing a topic exam means the topic is "tested out": Today stops recommending that topic's courses and moves to the next topic, then the next stage, unless the learner opened one of its lessons on purpose from Learn or the course map after the pass (`state.lessonPosition.pick` stamps `pickedAt`; the save time of a resume position does not count, so Back, a link or a reload never revives a lesson, ENGINE-BACKLOG 617). It is read from the saved exam attempts (`ZQ.content.topicPassed(id)`, `courseTestedOut(courseId)`), so nothing is stored per lesson, lesson `done` flags and progress stay as they were, and Learn still lists every lesson. A tested-out course is offered only when no other course has a written lesson left. Levels added to a topic after its exam was passed are therefore hidden from Today until the learner opens them on Learn. The Due queue is unchanged.
- For engine code: `ZQ.content.course(id)` carries `strand` (or `null`) and `strandNote`; `topicStrand(topic)` and `strandNoteOf(courseIds)` give a topic's strand and notes; `strandBadge(strand, note, cls)` returns the badge HTML.

## 10. Prep paths: "Interview prep" tags and the Prepare for page (ENGINE-BACKLOG 455)

Which lessons prepare for which assessment lives in one file, `app/content/prep.json`, not on the lessons. Firm facts go stale every cycle, so they are re-dated in one place; lesson ids never change; a path may name a lesson that is mapped in `course.json` but not written yet. Paths label lessons and list them in study order. They never unlock, lock or reorder anything.

```json
{
  "asOf": "2026-11-02",
  "paths": [
    { "id": "general", "name": "General interview prep", "kind": "general", "description": "One or two plain sentences.",
      "mocks": [],
      "steps": [
        { "ref": "mental", "priority": "must", "why": "One line, under 20 words." },
        { "ref": "puzzles/level-1", "priority": "must", "why": "..." },
        { "ref": "conditional/l3-shrinking", "priority": "should", "why": "..." } ] },
    { "id": "oa-trader", "name": "OA prep: trader", "kind": "stage", "stage": "oa", "track": "trader",
      "mocks": ["mock-oa-arith"], "steps": [] },
    { "id": "firm-optiver", "name": "Optiver", "kind": "firm", "track": "trader",
      "asOf": "2026-10", "source": "recruiting/l4-firm-by-firm", "reported": true,
      "mocks": ["mock-oa-arith"], "steps": [] }
  ]
}
```

- Top level: `asOf` (`YYYY-MM-DD` or `YYYY-MM`, required: when the mapping was last checked) and `paths`. No other fields.
- A path: `id` (kebab-case, unique), `name`, `kind`, optional `description`, optional `mocks`, `steps`, plus the fields of its kind. Unknown fields are errors.
  - `kind: "general"`: no `stage`, no `track`.
  - `kind: "stage"`: `stage` is `oa`, `interview` or `superday`, and `track` is `trader`, `research`, `strats` or `developer`, both required. One path per stage and track pair.
  - `kind: "firm"`: `asOf` (`YYYY-MM` or `YYYY-MM-DD`), `source` (a ref, usually the recruiting lesson the firm facts come from) and `reported: true` are required. `track` is optional.
- A step: `ref`, `priority`, `why`, and an optional `track` (for a firm that runs several roles; shown as a small role tag). Steps are in study order and the page shows them in that order.
  - `ref` is a course id (`mental`), a level (`puzzles/level-1`) or a lesson (`conditional/l3-shrinking`). A course or level expands to its lessons. A lesson that `course.json` lists counts even when its file is not written yet; the page shows it as "Not yet written".
  - `priority` is `must` or `should`.
  - `why` is one line of under 20 words, in the app's voice (British spelling, no exclamation marks, no em-dashes).
- `mocks` lists mock exam ids (`mock-` then kebab-case words). An id with no file yet is allowed; the page shows it as "Not yet written" and links the others to `#exam/<id>`. Name the base mock only: its fixed versions (`<id>-2`, `<id>-3`, section 5 "Mock versions") are grouped under it.
- Validator errors: a `ref`, `source`, `stage` or `track` that does not resolve; a malformed id, date or mock id; a `why` of 20 words or more or with a copy-rule fault; a firm path without `asOf`, `source` or `reported: true`; a repeated ref or mock in one path; an unknown field; `stage` or `source` or `reported` on the wrong kind. Warnings: a firm path whose `asOf` is over 12 months old (re-check it and re-date), a path with no steps, a lesson that two steps of one path both cover. `node tools/validate.mjs --prep <file>` checks a scratch copy instead of `content/prep.json` and leaves the manifest alone. When `prep.json` is valid it is listed in `content/manifest.json`.
- Where it shows:
  - A lesson on any path gets an "Interview prep" chip on its course map node; a course with any such lesson gets the chip on its Learn card. Never more than one chip. The chip's tooltip and the node's detail (card on desktop, sheet on a phone) list the stages and firms, for example "General, OA, superday. Optiver, SIG (reported, October 2026)." with a link to the path.
  - Learn has a "Prepare for an assessment or a firm" link under its heading, and Review has the same link in the "Mock assessments" card. Both open `#prepare`; `#prepare/<path id>` opens one path.
  - The Prepare for page lets the learner pick General, a stage with a role, or a firm. A path shows each step with Must or Should, done, in progress, not started or not yet written, its `why` line, the lesson count, then its mocks. A firm path says "Reported formats, as of <month year>" under its title, with a pointer to its source.
  - Path names are in the Today search (kind "Prepare"), so "Optiver" or "OA" finds them.
- "Quant path only" is unchanged: it hides pure courses from Learn as before, and a step that points at a hidden course still opens its map.
- Prerequisite locks (section 11) apply to a path: a step whose written lessons are all locked shows "Locked" and its first missing prerequisite, and a mock that names `requires` shows "Locked". Paths still unlock nothing.
- For engine code: `ZQ.content.prep()` is `{ asOf, paths }` (empty when there is no file); `prepPath(id)`, `prepSteps(path)` (each step with `lessons: [{ course, id, level, name, written }]`), `prepRefLessons(ref)`, `prepFor(course, lesson)` and `prepForCourse(course)` (the paths a lesson or course is on), `prepDetail(paths)` (the line above) and `prepChip(paths, cls)` (the chip markup, `''` for none). The page is `js/screens/prepare.js`, styled in `css/screens/prepare.css`; the chip is `.prep-chip` in `components.css`.

## 11. Prerequisites: `requires`, the met rule, test-out and Strict mode (ENGINE-BACKLOG 481 to 490)

A level stays locked until the levels (or lessons) it relies on are learned. The lists live in `course.json`, nowhere else; topics and stages carry no `requires`, and lesson ids are never renamed.

```json
{ "n": 2, "name": "Bayes' rule", "lessons": ["..."], "review": "review-2", "homework": "homework-2",
  "requires": ["conditional/L1", "counting-chance/L2", "markov/l3-never-leave"] }
```

- `requires` on a level is a list of references. `"<course>/L<n>"` means the whole level; `"<course>/<lesson-id>"` is for the few cases where one lesson is enough (a lesson listed on that course map, written or not). Any course may be named, including the same one (`"markov/L2"`). List direct prerequisites only: the engine follows the chain. Choose the smallest set the level genuinely uses.
- Defaults: the first level of a course with no `requires` is open. A later level with no `requires` implicitly requires the previous level of its own course. `"requires": []` makes a later level open.
- A lesson that needs less or more than its level adds `"lessonRequires": { "<lesson-id>": ["<course>/L<n>", ...] }` at the top of `course.json`. It replaces the level's list for that lesson only; the review and homework of the level keep the level's list. Rare: justify each one in the report. For the cycle check a `lessonRequires` entry draws its edge from the lesson's whole level, so a lesson that needs less than its level can still be reported as part of a cycle where the engine would not deadlock; restate the list at level grain if that happens.
- An exam file may carry a top-level `requires` in the same format (levels or lessons, any course). The engine honours it on any exam file, mock, topic exam or stage test: while one reference is unmet `#exam/<id>` shows the locked card (and the Prepare for page marks a mock Locked), with Open anyway outside Strict mode. No mock carries the list yet; a content pass adds it to each `mock-*.json`, naming the levels whose lessons the papers draw from (the smallest set, direct levels only). Do not put it on a topic exam or stage test: they are how a learner tests out, and the validator warns.
- **Entries with a reason (ENGINE-BACKLOG 551).** Any entry in a level's `requires` or in a `lessonRequires` list is a plain string (still valid everywhere) or an object `{ "ref": "<course>/L<n>" | "<course>/<lesson-id>", "why": "<one line>" }`. Exam files take plain strings only (the validator rejects objects there). `ZQ.prereq.entriesOf`, `refsOf` (the gating strings) and `whyOf` are the one normaliser; every reader goes through them (node tools load it with `createRequire`).
  ```json
  "requires": [ "conditional/L1", { "ref": "integrals/L3", "why": "Expected values of continuous variables are integrals." },
                { "ref": "ito/L3", "why": "Stochastic calculus gives the PDE link; a quick check helps.", "gate": false } ]
  ```
  - Every cross-course entry (the ref's course differs from the level's course) should carry a `why`: one line, under 20 words, no em-dash, saying what the later level uses. The validator warns on a cross-course entry without one and prints `Requires: N cross-course edges, M without why`; `node tools/validate.mjs --strict-why` makes each an error (turn it on once the content pass is done). A same-course entry needs no `why`.
  - `"gate": false` makes the entry a **diagnostic**: it never locks, never counts in the closure, and needs a `why`. Where it is unmet the lock card, the lesson start screen and the Learn node card show "Check first: <level name>. <why>" with a link "Sit its review as a check" (`#review/...`, only when that level's review is written). Use it where the earlier level helps but is not worth a lock.
  - Where a level is locked, the lock card shows each missing prerequisite's `why` under its row, and the Learn node card and the Prepare step show the first one.
- **Route limitation.** The gating closure of a course, level, lesson or mock (implicit previous-level edges and `lessonRequires` included, `gate: false` left out, the course's own levels excluded) may reach a level with no written lesson. Under Strict such a level can never be met, so Learn (course card, node card, lock card) and Prepare (each step and the path header) show "Route limited: <course name> unwritten" ("partly unwritten" when some of its lessons exist), one chip per course. It is computed from the content, nothing is authored; it disappears when the lessons are written or the edge is cut or made a diagnostic. On the course card it replaces the static `limited` text that `readiness-sums.mjs` writes into `readiness.json` for a course starting "route limited" (the generated entry for pdes can go once nothing else reads it).
- **Closure tool.** `node tools/closure.mjs --role trader|researcher|developer|strats|derivatives` or `--target <course>/L<n>|<mock id>` prints levels, courses, mapped and written lessons, the courses in the closure and the unwritten courses reached; `--json`, `--edges` (the cross-course edges inside the closure with their `why`). A level target counts what it requires, not itself; a role is the union of its present mocks (`readiness.json`); `--target mock-superday-trader` gives 107 levels, 35 courses, 470 lessons. `--proposal-template <file>` writes every cross-course edge in `course.json` as `{ "from": "<course>/L<n>", "ref": "...", "why": "", "action": "keep" }` (plus `"lesson"` for a `lessonRequires` edge) for a content agent to fill; `action` is `keep`, `cut` or `diagnostic`.
- Not named in the lists: `strand`. A Pure course never gates a Quant or interview course; interview courses (topics 0.7, 3.3, 3.5) gate only on what their briefs name.

### The met rule

A level reference is met when any of these holds:

1. the level review (`review-<n>`) has a passed attempt: the review's `pass` share (`"pass"` in the review file, fallback `PASS = 0.8` in `prereq.js`, the same as the quiz mastery bar) of its auto items, and in the same attempt every essential skill at or above `SKILL_FLOOR = 0.7` of its items (the essential skills of a level are the skills tagged on its review's items, so tag each item with the skills you want the level to prove; a skill on a single item must be right). The pass is remembered and a later weaker attempt never removes it;
2. the level's topic exam is passed (tested out) and one passing attempt covers every essential skill of the level at `SKILL_FLOOR` over its auto rows (a skill the exam did not draw counts as uncovered); otherwise the pass is a badge for that level and does not meet it;
3. the stage exit test of the level's stage is passed, under the same coverage condition as item 2;
4. a test-out of that level was passed (below);
5. the level was recorded met when a save from before gating was first loaded (below), or has no written review and every lesson on its map is written and finished (a half-written level without a review is never met).

A lesson reference is met when that lesson is finished and its quiz mastered (80%), or its level is met. A lesson in which more than `REVEAL_CAP = 0.25` of its gradable screens (task screens plus quiz items) were revealed with Solve does not count as done for prerequisites or progress figures (`state.lessonCounts`); it is still finished, never locks, and an honest replay of the revealed screens makes it count. Revealed answers never raise a skill score. A missed quiz item always joins the redo queue, even when the quiz reached mastery. Opening a lesson never counts. A met level stays met: the engine records every level it finds met in `state.prereq.met`, so nothing that was unlocked is ever locked again, a finished lesson is never locked, and a level opened early stays open. Old saves: on the first load after gating shipped, every level whose lessons are all written and finished is recorded met, once.

A met level is open as a place to work: its lessons, review and homework open even when its own references are unmet, because it was met by mastery shown (a test-out, a review pass, a topic or stage test). A lesson with its own `lessonRequires` entry keeps that list. A level the learner has started (one lesson finished) is likewise kept open for its remaining lessons, review and homework, recorded in `state.prereq.started`; it does not count as met for dependants and You does not count it. Finished lessons are never locked.

A level is locked while any direct reference is unmet; its lessons, review and homework are locked with it. The locked card lists the unmet references and, transitively, what those need. A reference to an unwritten level can never be met (its lessons cannot be finished and it has no review to test out with), so the dependent level stays locked until it is written.

**Performance task (ENGINE-BACKLOG 529).** When a level carries a performance task (section 5; `content/manifest.json` `perf` lists them), rules 1 to 4 each need one more thing: the task is passed. This is an extra AND, so a review, exam or test-out pass at the floor does not meet the level until the task is passed, and a self-marked task never meets a level alone. A level without a task is unchanged, and so is a level whose task the verb rule does not match: that task is practice only and `perfNeeded` returns null for it (the manifest row has no `gates`, section 5; ENGINE-BACKLOG 549). Rule 5's grandfathered record from an old save is exempt; the "no written review, every lesson finished" path needs the task too. How it is stored and read: `state.perf["<course>/L<n>"] = { item, kind, how, at }`, written once by `ZQ.state.perf.pass({ course, level, item, kind, how })` when a homework or review row with `perf` set comes back `ok` (a code or numeric row stored `how: auto`, a longform row `how: self`, a reviewer-entered `external`). A later miss never removes it. `ZQ.prereq.perfNeeded(course, lv)` and `perfPassed(course, lv)` read it; the locked card and the test-out result say "performance task not passed" while it is missing. A test-out that passes while the task is not passed is recorded as a badge only: the level stays unmet until the task is passed.

The test-out below applies the same skill floor to the skills of the items it drew. Items 1 to 3 read the auto and external part of a result only. Self-marked items do not count (section 13).

### What the learner sees

- Course map: a locked node carries a lock and no "Jump ahead"; its card offers "See what is missing". `#lesson/...`, `#review/...` and `#homework/...` for a locked item open the locked card instead.
- The locked card groups Stage, then Topic, then Course, then level or lesson, each with a count ("Stage 1 > 1.5 Probability > Markov Chains: Level 1, 3 of 4 lessons finished, review not passed"). Direct prerequisites come first and are open; indirect ones collapse into one line per stage ("and 14 more in Stage 1"). "Start here" opens the earliest missing lesson whose own prerequisites are met (or its review when the lessons are done).
- Test-out: each missing level with a written review offers "Test out" (`#testout/<course>/<n>`). Up to 6 items from `review-<n>`, seeded by level and attempt and shuffled (a retake draws items not yet shown first; the record keeps the ids in `state.prereq.testouts[...].seen`, so a review of 12 or more items gives a fully new second paper and a review of 6 repeats it, so give a level that others require 12 or more review items), no hints, one try each, passed at the review's pass share (5 of 6 at 0.8) with every drawn skill at `SKILL_FLOOR`. A pass marks the level met. A miss lists the lessons to revisit (found by skill) and the test-out can be retaken after 24 hours. It earns no XP or mastery points and adds nothing to the redo queue. A level with no written review cannot be tested out of: its lessons must be finished.
- Strict mode: You, Settings, Study plan, "Strict prerequisites" (`settings.strictPrereqs`, on by default). On: no "Open anyway"; test-out stays. Off: the locked card shows a secondary "Open anyway", which opens the item and records the level in `state.prereq.opened`; You shows the count as "opened early".
- Today and Learn choose the next lesson among unlocked ones. If the lesson Today would have chosen is locked, Today says so in one line and offers "Start here". The Prepare for page marks a blocked step with a lock and its first missing prerequisite. The interview bank already gates items by their own `requires` (lessons finished); that is unchanged.
- Refresh: a met prerequisite whose review has not been taken for 30 days shows a "Refresh" chip above the dependent lesson's first screen, whatever kind of screen it is (a link to its review, which is open because the level is met). It never relocks.

### Validator rules (`tools/validate.mjs`)

Errors: a reference that is not `<course>/L<n>` or `<course>/<lesson-id>`; an unknown course, level or lesson; a level that requires itself; a reference from an earlier stage to a later one; a cycle across all courses (printed as `a/L2 -> b/L1 -> a/L2`); `requires` not a list (also on an exam file); `lessonRequires` not an object or naming a lesson not on the map; a level whose `requires` names its own level or one of its own lessons. Warnings: `requires` on a topic exam or stage test; a reference to a later topic in the same stage; a reference to a level with no written lesson or a lesson not written yet (the dependent stays locked until it is written); a written level whose implicit previous level has no written lesson; a reference listed twice.

### For engine code and playthroughs

`ZQ.prereq` (`js/prereq.js`): `levelMet`, `lessonMet`, `refMet`, `lessonLocked`, `levelLocked`, `itemLocked`, `courseLocked`, `missingFor(course, lesson)`, `missingForLevel`, `missingRefs(refs)` (each `{ direct, indirect, start, count }`), `refreshFor`, `strict`, and the test hooks `unlock(course, id)` and `unlockRefs(refs)`, which mark every prerequisite of a lesson, review, homework or mock met. `node tools/playthrough.mjs --lesson`, `--set`, `--exam` (and `--all`) call them before playing the target; `--bank` and `--drills` are not gated by levels. `--routes-only` also checks: a fresh profile has a Stage 0 first lesson open and a Stage 3 level 2 lesson locked with a correct card and a "Start here" that opens; Strict hides "Open anyway" and the switch is on; outside Strict the override opens the lesson and counts; a test-out unlocks and a failed one waits 24 hours; an old save with a finished level is grandfathered; the course map draws the lock.

## 12. Readiness contract: `readiness.json` and how roles gate (PLAN 2c item 2)

`app/content/readiness.json` is generated. Never edit it. The source is the classification tables in `docs/readiness.md`; run `node app/tools/readiness-sums.mjs --write` after changing a table, a `course.json` map or a mock. The same script without `--write` fails if the markdown blocks or the JSON are out of date. The validator only checks the JSON's shape and lists it in the manifest.

The file holds, per role key (`trader`, `researcher`, `developer`, `strats`, `strats-deriv`, `undecided`): each course's status (`required`, `recommended`, `optional`), totals (lessons and hours, written and unwritten, for required, recommended and the Learn header) and the mocks present and missing. `strats-deriv` is a sub-route of Strats, in the JSON only; it is not a profile track. The profile tracks are Trader, Researcher, Developer, Strats and Undecided (`ZQ.content.readiness.roleKey`).

What the engine does with it:
- Today picks next work from required courses first, then recommended, never optional. Optional courses stay on Learn. Undecided keeps the old order.
- Under Strict (`settings.strictPrereqs`), a `requires` edge into a course that is optional for the profile's role is advisory: it never locks, and the course map adds a note to the lesson ("it relies on ... which is optional on your track"). Undecided, and any role for which the target course is required or recommended, still block. No `course.json` edit is needed; `ZQ.prereq.advisory(ref)` is the rule.
- The Learn header shows one total for the role: required plus recommended, written and unwritten stated separately. Undecided shows the shared foundation.
- A course card shows "route limited: odes, numerics unwritten" for a course listed in `LIMITED` at the top of the generator's JSON section (today `pdes`). The script fails when a course it names as missing gains a written lesson, so the note cannot go stale.

Authors writing a `requires` edge into a course that is optional for a role should still write it: it keeps the order for roles that need it.

## 13. Result provenance: `how` (ENGINE-BACKLOG 521, PLAN 2c item 3)

Every graded row the engine stores carries `how`: `auto` (the app marked it), `self` (the learner ticked it) or `external` (reserved for a reviewer-entered record; stored and counted like `auto`). A row without `how` reads as `auto`.

- Self rows: a `longform` item (kind `longform`, a `longform` widget, or an item with a longform part) in homework, a topic exam or a superday mock. Everything else, code and sketches included, is `auto`. The mock and stage "checks" (`no-lookup`, `game-aloud`, `story-aloud`) are self ticks too; they are stored on the attempt as `checks: [{ name, how: "self", ok }]`.
- A self row never touches `skills[s]` (Elo, mastery points, `seen`, `correct`) and earns no mastery points or item XP. The homework base XP stays. Self results go to `state.selfMarked[skill] = { seen, correct, lastAt }`, shown on You under "Self-marked", never in the mastery map. A self miss still joins the redo queue.
- **Written items in an exam (ENGINE-BACKLOG 589).** A `longform` item, or an item with a longform part, in a topic exam, stage paper or mock is marked by the learner after the paper is submitted, off the clock: the page shows each written answer's model answer and rubric, the learner ticks the rows (as on the homework page), and Finish marking scores the paper. The item's credit is the rubric points ticked over the rubric's points (a longform part keeps the usual share of parts, a part counting as right at 7 of 10); the row is stored `how: self`. Skipping the step scores 0 and the result page says so. A `navigation: forward` paper stays forward-only for answers, because marking happens only after submit.
- Met rule: an exam or review counts towards a level only if it still passes with self rows removed from numerator and denominator, against the same pass mark (an absolute `passNet` scales to the auto share). The result is stored at finish time: `passedAuto` on each exam attempt and on the review record. Mock and stage checks are left out of it. An attempt with no auto item cannot meet anything. Homework never feeds met, and no prerequisite or readiness code reads `selfMarked`.
- Old saves: a row, exam attempt or review without the new fields loads unchanged and is not rewritten. Missing `how` reads `auto`; old longform rows and checks cannot be told apart in the stored aggregates, so old Elo and mastery points still include any earlier self ticks (not split, not invented). A review record without `passedAuto` uses `passed` (level reviews hold no longform). An exam attempt without `passedAuto` counts as its `passed` when the exam holds no self item and no check part, and does not count when it does (or when there is no manifest). The validator writes `selfExams` into `content/manifest.json`: the exam ids holding a longform item, a longform widget, a part with a longform widget, or a `check` part (the test `state.provenance` uses). A level already in `state.prereq.met` stays met, and the engine records met levels on every change. One helper, `ZQ.content.examPassedAuto(id)` and `examPassedAt(id)`, applies this rule for prerequisite met, `topicPassed` (Today and Learn) and the refresh date.
- `ZQ.state.provenance(item)` returns `self` or `auto` for an item spec; build result rows with it.

## 14. Workload: one function, `ZQ.hours` (PLAN 2c item 11, ENGINE-BACKLOG 559 to 563)

Hours are computed in one place, `app/js/hours.js` (`ZQ.hours` in the app, `require('../js/hours.js')` in node tools). Nothing else adds up hours.

- A topic's hours are stored on the topic in `curriculum.json` (`hours`). A stage's hours are **never stored**: they are the sum of its topics' hours. A stored stage `hours` field is ignored by the engine and warned about by the validator; `node app/tools/apply-item11-content.mjs` removes it.
- A topic's hours are shared across its courses, and a course's across its lessons, by weight: 1 for a short lesson, `minutes / 14` for a workshop or project (14 is the median short lesson). With no workshop or project the shares equal the mapped-lesson counts. A topic's total never changes with `session`; a workshop only takes a larger share of it.
- A role's hours are the totals in `content/readiness.json` (required plus recommended is the Learn header), written by `node app/tools/readiness-sums.mjs --write` through `ZQ.hours`. After changing any lesson's `session` or `minutes`, run it with `--write`; `apply-item10-content.mjs` does this itself.
- Figures quoted in prose come from `node app/tools/curriculum-hours.mjs` (`--write` rewrites the block in `docs/curriculum.md`, `--check` also compares the stage figures in its prose). Learn's stage cards, its header and "about N months at 15 h a week" (`ZQ.hours.months`) read the same function.
- A topic that stores 0 hours (3.2 and 3.4) is not invented: `curriculum-hours.mjs` lists the figure its lesson minutes would give beside the 0.

## 15. Capstones: `capstones.json` and the role verdict (PLAN 2c item 8, ENGINE-BACKLOG 564 to 569)

`app/content/capstones.json` is an optional array with one record per role (`trader`, `researcher`, `developer`, `strats`, `strats-deriv`; not `undecided`). The reviewer fills it by hand; the app only reads it. Fields: `role`, `project` (free text; the researcher's is `momentum-rep`, or another project with `"equivalentOf": "momentum-rep"`), `repo` (https URL or empty), `reviewer`, `date` (YYYY-MM-DD or empty), `rerun` (`pass`, `fail` or empty: the result of rerunning the project from a clean checkout), `defence` (notes), `external` (boolean). An all-blank record with `external: false` is valid and means "not done".

A record is complete only when `external` is true, `repo`, `reviewer` and `date` are non-empty and `rerun` is `pass`. A role is ready only when every level of its required courses (`readiness.json`) is met and its record is complete: `ZQ.content.readiness.roleState(role)` and `.verdict(role)`. No screen may print "ready" as a role verdict from anywhere else. Exam "Mastery map estimate" lines are per-exam estimates and say so.

The validator (`tools/capstone-rules.mjs`) errors on an unknown role or field, a wrong type, a duplicate role, `external: true` with a blank repo, reviewer, date or rerun, a malformed URL or date, and a researcher project that is not `momentum-rep` or its equivalent. A missing file is fine. The You screen shows the records read-only in a Capstone card.

**Oa drills and code tasks.** A verified drill of pack `oa` (file `pack: "oa"` or an id starting `oa-`) counts as passing the code performance task of its level. The level is the drill's optional integer `level` (drill file or `drills/index.json` row), else the lowest level of the drill's `course` that has a gating code task (coding-int level 1 today). Self-marked and non-code tasks are unaffected.
