# CI: the acceptance suite

`.github/workflows/acceptance.yml` runs the session's acceptance suite on GitHub Actions, on the real jsDelivr (Pyodide, YoWASP and MathLive are not served locally).

**What runs**
- `static`: `validate.mjs` (0 errors), `same-course-reuse.mjs --all` (engine item 972: no unwaived `[same-course-reuse]` error in any problem set; waivers in `app/tools/same-course-waivers.json`, about ten seconds; `AUTHORING.md`, same-course reuse), `readiness-sums.mjs`, `ci-coverage.mjs` (fails if a `tools/test-*` file is in no job or in two), `grade-all.mjs` (keys, bands and slip routing of all content, no browser), and the 17 tests that need no browser.
- `tests-browser`: three legs, `grading` (answer forms, engine runtime desktop and `--mobile`, problems, fluency; they get a lean local copy of the Compute Engine and MathLive), `ui` (check-first and today-tested-out desktop and `--mobile`, the overflow and tall-shot tests) and `python` (bank code, drill page, drill recursion, planted check: Python 3.12 packages, Pyodide and YoWASP from the CDN).
- `validate-tests`: the 19 `test-validate-*` files, each called by name with no flags (band-rules is given the Compute Engine through `ZQ_LOCAL_CDN`).
- `play`: `playthrough.mjs --all --shard i/N --no-routes`, N shards (default 16) times desktop and `--mobile`. `extras`: `--problems all` (2 shards), `--fluency-all` (4), the drills (3, by naming them with `--drill`, the session play in part 1) and `--routes-only`, each desktop and `--mobile`.
- `number-scripts`: `tools/test-run-number-scripts.mjs`, then `tools/run-number-scripts.mjs` over every number script (`docs/reports/*-numbers*.py` and the `*number*.py` under `docs/briefs/*-scripts/` and `docs/reviews/*-scripts/`, 358 today), 4 at a time with a 150 s limit each, in full on every push and dispatch (about 8 minutes). Python 3.12 with `.github/actions/zq-setup/requirements.txt`. It prints only failures and one count line. It is red on a script that fails or times out and is not in `tools/number-scripts-known-failing.txt`, and on a listed script that passes or a listed path that is gone. The list holds only scripts that fail because the content is wrong (one `path | reason` per line, evidence in `docs/reports/number-scripts-ad.md`): repair a script that is stale or slow, never list it. Locally: `node tools/run-number-scripts.mjs --python <venv>/bin/python [--only <text>] [--changed [<base-ref>]] [--timeout <s>] [--jobs <n>]`; `--changed` runs the scripts whose own file changed or that name a changed course, exam or bank file. Scripts run in their own folder; the Fluency scripts draw 60 seeds (`FLUENCY_N=200` for the old 200).
- `acceptance`: needs all of the above and fails unless each succeeded. Read this one status; its job summary lists every job.

**How to trigger**: push to `claude/amazing-wright-d4mx7i` touching `app/**` or `.github/**`, or Actions, acceptance, Run workflow with `shards` (1 to 64), `suite` (`full`, `static`, `tests`, `play`, `extras`) and `mode` (`changed`, `full`; see the green-hash cache below). A newer run on the same ref cancels the older.

**How to read a failure**: open `acceptance`, find the red job, open its log. Each step ends with the last 40 lines; `ci-run.sh` prints a group per command and a table of `ok` and `FAIL` lines with seconds; play and extras then print their `FAIL` lines again. Re-run the failed leg once before treating it as yours. To reproduce locally, run the command shown in the group from `app/` (add `--local-cdn <pkgs>` if the network is closed).

**Expected minutes** (estimates from timings in a slow sandbox, not measured on Actions): one play leg 20 to 25 (128 items at about 10 s), extras legs 8 to 12, `static` 12, `validate-tests` 10 to 15, `tests-browser` legs 10 to 25, first-run Playwright download 1 more. Wall clock about 25 to 30 minutes; about 1000 runner minutes a full run (the repo is private, so metered). `--drills` has no `--shard`, hence the `--drill` split; the unsplit run would be about 25 minutes desktop. `--all` already includes the problem and Fluency sets, so `extras` plays those a second time in their own profile by design.

**The green-hash cache (engine pass AC part 5)**

What it does: on a push, each `play` and `extras` job restores its own cache file, selects with `playthrough.mjs ... --changed --list` (no browser, about a second), installs Playwright only if `changed: K of N` has K above 0, replays only the K items with `--changed --cache tools/.green-cache.json`, and saves the file. A job with K of 0 skips the browser install and the run and finishes in well under a minute. `ci-green.sh` holds the selection and the "did the file grow" test, so they can be run locally in their cheap form.

Modes: a push runs `changed`. `workflow_dispatch` has an input `mode` (`changed` or `full`, default `full`); the weekly schedule runs `full`. `full` restores nothing and does not pass `--changed`, so everything replays; every green is still recorded and the file is saved, so a full run reseeds the cache. The `acceptance` summary states the mode and lists `<job>: changed K of N` for every play and extras job, with a total (each job uploads one line as an artifact; a cancelled job uploads none).

Keys: each job owns one file. It restores with `restore-keys: green-<job>-` (the newest cache under that prefix wins; the trailing `-` keeps shard 1 from matching shard 10) and saves under `green-<job>-<run_id>-<run_attempt>`. `<job>` is `play-<N>-<vp>-<shard>` or `extras-<vp>-<part>`. Reasons:
- Caches are immutable per key and 52 jobs write at once. Per-job keys never collide, and the run id and attempt make a re-run save a new entry instead of being refused. No merge job is needed, so nothing waits on the slowest leg and one failed leg cannot stop the rest saving.
- Cancelled run: the save steps are guarded by `!cancelled()`. A killed `playthrough` has written batches of passes but has not done its final sweep (which drops items whose id appears in a late failure or console error), so its file is not trusted; it is not saved and the job's previous cache stays the newest. Its greens are lost, never wrongly kept. The same holds for a job timeout.
- Failed job: the save step still runs. The file holds only items that passed (a failed item is never recorded, and the final sweep has run), so the passes are kept and the failures replay next time.
- The built-in post step of `actions/cache` is not used, because it saves on failure without those guards and cannot save under a second key.
- The file is saved only when it differs from what was restored (`ci-green.sh dirty`), so an all-green no-change run adds no cache entry.
- Nothing wrong survives restoring a cache. The file is keyed `kind|id|mode` with a hash inside. The mode is the viewport: a desktop green is not read for `--mobile` or `--tablet` (tested), and the job id carries the viewport as well. Branches: a cache saved on a branch is visible only to that branch and the default branch, so another branch starts empty and replays everything. The engine hash covers `js/`, `css/`, `index.html`, `vendor/`, `playthrough.mjs`, `green-cache.mjs`, the pinned CDN versions found in the app files (MathLive, Compute Engine, Pyodide, YoWASP), and the installed Playwright version (the Chromium build follows from it). A different engine of any of these shows everything as changed. What it cannot see: the runner image (`ubuntu-24.04` is a moving label), Node 22 minor versions, and the Google Fonts or jsDelivr content behind an unchanged version string. The weekly full run exists for those.
- The Playwright pin lives in `.github/actions/zq-playwright` (install and browser cache key) and in `zq-setup` (`ZQ_PLAYWRIGHT_VERSION`, used for the hash before the browser is installed; an installed package wins when there is one). Change all three together; changing them invalidates every cache, as it should.
- A cache is stored for seven days without use, then evicted, which is a harmless full replay. Entries for items that no longer exist stay in a file until then; they are small and never match.

Shards and the cache (engine item 973): a job's cache holds only the items of its own shard, so the partition must not move when content is added. `--shard i/n` therefore keeps the items whose sha1 of `kind|id`, mod n, is i-1, not the items at every n-th position. Before this, CI run 10 (12 new problem sets) replayed 39 of 54 items in each `extras problems` mobile job (about 18 minutes, against 6 new sets): the new sets shifted every later set into the other shard, whose cache did not hold it. No hash was wrong: the item hashes of runs 9 and 10 differ for 5 of 94 existing sets, the five edited files. The same shift hit the `play` legs for every problem set, fluency set and exam after a new item. The price is balance: with 16 shards of the full list a shard holds 112 to 146 items (mean 128) instead of exactly 128, so the longest leg of a full run is about 14% longer. The first push after this change replays everything once (every shard's cache is keyed to the old partition). `test-playthrough-changed.mjs` checks that adding two problem sets moves no other set.

Tests: `test-ci-cache-keys.mjs` models this scheme (immutable keys, newest-prefix restore, branch scope) with two jobs, a failing one and a cancelled one; `test-playthrough-changed.mjs` covers viewport and Playwright-version invalidation.

**Weekly schedule**: `schedule` runs `full` on Sundays at 03:17 UTC. GitHub runs a scheduled workflow from the default branch only, and the default branch here is `main`, which holds no `.github/` and no `app/` yet (`git ls-tree origin/main`). The development branch `claude/amazing-wright-d4mx7i` is not the default, so the schedule will not fire until the workflow is merged to `main`. Until then, start a `workflow_dispatch` with `mode` full by hand now and then. Once merged, the scheduled run builds `main`, saves its caches on `main`, and those are readable by every branch.

**Reproducing CI locally (engine pass AC part 4)**: `tools/fetch-local-cdn.sh <pkgs>` also fetches the Google Fonts stylesheet and woff2 files into `<pkgs>/fonts/` when the network allows; `playthrough.mjs --local-cdn <pkgs>` then serves them instead of empty CSS, so text widths match CI. `ZQ_CDN_DELAY_MS=1500` makes every local-CDN file wait that long, to mimic a slow jsDelivr (it reproduces the Fluency "Loading the maths editor" race). Tests that play a temporary copy of `app/` run `playthrough.mjs` from `tools/` in place with `ZQ_APP_DIR` set, because a copy in the OS temp dir cannot resolve the workspace `node_modules`; the setup action also exports `NODE_PATH` for the loaders' fallback.
