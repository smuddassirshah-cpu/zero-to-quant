# Concept audit, round 2: systems L4 (l15 to l18, review-4, homework-4)

Blind read (no earlier review, answer check, audit or report of this level opened before the ledger and these findings were committed). Ledger: `docs/reports/audit-systems-4-r2-ledger.md` (197 rows). Checks: `docs/reports/systems-L4-concepts-r2.py` (exit 0). Severities: `wrong`, `imprecise`, `misleading`. Each fix is paste-ready.

## Findings

1. l16-ring-buffer.json | screens[5].prose | imprecise | "A `release` store publishes everything written before it, and an `acquire` load sees it" drops the condition: only an acquire load that reads the released value synchronizes with it. A learner carries away that any acquire load sees the writes. | [atomics.order]/2 (C++17): a release operation A synchronizes with an acquire operation B that reads the value written by A (or one in its release sequence); Williams, *C++ Concurrency in Action* 2nd ed., 5.3.3. | Replace the second sentence with: "A `release` store publishes everything written before it, and an `acquire` load that reads that store sees it."

2. l16-ring-buffer.json | screens[6].explain | imprecise | "A data race is two threads touching one variable, at least one writing, with nothing ordering them" omits that the variable is non-atomic. As stated, two unordered relaxed accesses to an atomic counter would be a data race, which they are not; the lesson's own counters are atomics with no further ordering between their writer and reader. | [intro.races]/21: conflicting actions in different threads, at least one not atomic, neither happening before the other; Williams 2nd ed. 5.1.2. | Replace the first sentence with: "A data race is two threads touching one non-atomic variable, at least one writing, with nothing ordering them."

3. l17-measuring-latency.json | screens[5].explain | imprecise | "a few slow requests move it little": on this screen 1% of requests at 1,000 µs doubled the mean, from 10 to 19.9 µs. What the lesson needs is that the mean stays far below the tail value, not that it barely moves. | Arithmetic of the screen's own data (`sim: l17-s0`); the next screen (screens[1].explain) correctly says the mean "barely moves" only from 19.9 to 20.9 for one extra slow request. | Replace the first sentence with: "The mean is a total divided by a count, so a few slow requests leave it far below their own latency: 19.9 µs here, against 1,000."

4. l17-measuring-latency.json | quiz[0] (q17-rank).question | imprecise | The key 8 is right only by nearest rank, and the item does not name the convention. By linear interpolation (Hyndman and Fan type 7, the NumPy and pandas default) the p75 of 1 to 10 is 7.75, and the slip 7 is what rank 7 reads, so a learner who used the interpolated rule is marked wrong without being told which rule the item wants. review-4 `r4-p60` says "by nearest rank" for the same kind of question. | Hyndman and Fan (1996), *Sample Quantiles in Statistical Packages*, definitions 1 and 7; `sim: q17-rank` (nearest rank gives 8). | Replace the question with: "What is the p75, by nearest rank?"

5. l18-feed-handler.json | screens[7].explain | misleading | The rule taught is "a larger number is new data, so it is applied" with the skipped numbers "counted for a later repair", and the pipeline of screen 0 runs the strategy straight after the book update. A book that has applied increments past a gap is missing updates (an add never seen, a cancel for it), so trading on it is the wrong habit. The lesson never says the book is untrustworthy until the gap is repaired; the homework model answer (h4-handler-aloud §3) does say "The gap is repaired from a snapshot". | Nasdaq MoldUDP64 specification (a receiver that detects a gap requests retransmission before processing further); CME MDP 3.0 market data recovery (after a gap the book is rebuilt from the snapshot feed); homework-4 h4-handler-aloud model §3 and §6. | Replace the explain text with: "A larger number is new data, so it is applied and the skipped numbers are counted. The book is now missing those updates, so mark it stale and repair it from a retransmission or a snapshot before the strategy trusts it. A smaller number is a duplicate or a late arrival and is dropped." Optionally add to screens[7].prose, after "Handle loss and partial reads on purpose.": "Repair a gap before trading on the book."

6. homework-4.json | items[0] (h4-latency-hist).prose | imprecise | "Keeping every sample would allocate" is false for a fixed array sized up front, which is the lesson's own rule (l15 screens[8]); what forces allocation is an unbounded, growing store. | l15 screens[8] and screens[6] (a `std::array` or a reserved vector allocates nothing on the hot path); HdrHistogram README (fixed-size counts, no allocation on record). | Replace the sentence with: "Keeping every sample in a growing container would allocate."

7. homework-4.json | items[1] (h4-sizing).parts[4].question and explain | imprecise | "fits a 32,768-byte L1 and so stays resident" makes fitting sufficient for residency. It is necessary only: the code, the other data each message touches and set associativity also decide what stays, as the `all` option's own `why` says ("What is touched is what matters"). | Hennessy and Patterson, *Computer Architecture: A Quantitative Approach* 6th ed., B.1 to B.3 (capacity and conflict misses). | Replace the question with: "Which of these fits a 32,768-byte L1, so it can stay resident?" and the last clause of the explain with: "so only the ring can stay resident."

8. homework-4.json | items[3] (h4-two-hosts).parts[3].options.avg.why | imprecise | "it moves the wrong way as hosts differ in size" gives no reason a learner can use. The fault of an unweighted average of percentiles is that it ignores how many requests each host served. | Tene, "How NOT to Measure Latency" (percentiles cannot be averaged); derivation: with host A at 10,000 requests and host B at 100, the average of the two p99 values weights B's tail as much as A's. | Replace the `why` with: "The average is a number no request had, and it ignores how many requests each host served: a quiet slow host counts as much as a busy fast one."
