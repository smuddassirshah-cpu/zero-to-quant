## Errors

- docs/briefs/cpp.md | P-move-buffer, tests and "plausible learner slips" | error | A move constructor that forgets `other.data_ = nullptr` (the commonest move slip: both objects then `delete[]` one block) passes all 13 tests in the app (0 of 13 failed, clang 21 + libc++ + the app's `leakCheck`, mutant `R_move-ctor-forgets-null`). Natively glibc aborts on the double free (6 of 13 fail), which is why the brief's run reports the slip caught; the app's allocator (wasi dlmalloc) frees twice silently and `leakCheck` counts only blocks never freed or freed with the wrong form. The brief's claim that every slip "fails at least one test in every compiler and standard" holds for the native harness, not for the app. | Add a public `const double* data() const { return data_; }` to the starter and test `Buffer a(3, 1.5); Buffer b = std::move(a); a.data() == nullptr` (and again after `b = std::move(a)`), which fails deterministically. Re-run in the app, not natively, before claiming a slip is caught.
- docs/briefs/cpp.md | P-copy-samples test 9 (`a = r; a.get(0) + a.get(1)`) and P-vec test 14 (`v.push_back(v[0]); v[1]`), and the "caught 20 of 20" and "caught 28 of 28" lines | error | Both tests detect a slip only by reading memory the learner's wrong code has already freed (delete-first assignment; freeing the old block before building the new element). That is undefined behaviour in the test's observation, and in the app neither slip is caught: `delete-first-no-guard` 0 of 13 failed and `frees-before-building-new` 0 of 15 failed (clang 21 + libc++ + app wrappers). The brief admits "best effort" but still lists both mutants as caught. | Remove both mutants from the "caught" lists and say so in the problem notes. For `push_back(v[0])` use the hidden `Counted` to detect a destroyed source deterministically: let `~Counted` set `v = -2` and make the test `Vec<Counted> v; v.push_back(Counted(7)); v.push_back(v[0]); v[1].v` expect 7 (the slip that destroys old elements before copying the argument then fails, with no read of freed memory). For `a = a` keep the test only as a well-defined check for correct solutions and do not describe it as catching delete-first.
- docs/briefs/cpp.md | l21 S9 explain, S11 explain, homework 9 model answer ("a load and an indirect jump", "one extra load") | error | A virtual call makes two dependent loads (the object's vptr, then the table slot) and an indirect call; S9's own three steps say so (load the vptr, index the table, call). "One extra load" contradicts them. | "two loads and an indirect jump" in S9, S11 and homework 9.
- docs/briefs/cpp.md | l21 S11 slip `inline` ("A virtual call through a base pointer cannot be inlined") and the explain ("blocks inlining") | error | Not true in general: a compiler inlines a virtual call whenever it can prove the dynamic type (devirtualisation, `final`, a local object, link-time optimisation). The brief's own `final` slip says exactly that, so two options on one screen contradict each other. An interviewer will push on this. | `inline`: "`inline` does not tell the compiler which function a call through a base pointer reaches." Explain: "...and usually stops inlining, because the compiler does not know the target. With one known type, a template gives the same code with no lookup."
- docs/briefs/cpp.md | l20 S8 slips `copy` and `warn` ("So neither exists"; "no constructor is left that takes `Order&&` or `const Order&`") | error | `struct Order { std::unique_ptr<Fill> fill; ~Order() {} };` has an implicitly declared copy constructor that is defined as deleted; it exists and takes `const Order&`, and overload resolution selects it for `std::move(a)`. That is why the message reads "call to implicitly-deleted copy constructor". No move constructor is declared. The wording is the opposite of what a follow-up question ("is it deleted or absent?") needs. | `copy`: "The copy constructor is selected, and it is deleted because `unique_ptr` cannot be copied." `warn`: "It is an error, not a warning: the only candidate is the deleted copy constructor."
- docs/briefs/cpp.md | l23 S8 key ("`a = a` (or two pointers on one object) could otherwise free the object before it is taken again") | error | With two distinct owners of one object the count is at least 2, so dropping first cannot free it. Only a self-assignment (or an assignment from something that is itself kept alive only by the object being released) reaches zero. | Key: "`a = a`: the count could fall to zero and free the object before it is taken again." Drop the parenthesis.
