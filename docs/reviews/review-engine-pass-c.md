## 3. Findings

### Errors

1. **error** | `app/tools/playthrough.mjs` 655 | The draw check's drill pool is `name === '*' || d.pack === name || d.id === name`. The engine (`mock.js` 129) and the validator (`validate.mjs` 1873) also match an id prefix `<pack>-`; the merge dropped it here. Scenario: a mock that draws `drills/sample-cpp` (or any real pack named by its id prefix, which is how the brief's `ci-`, `rq-`, `sy-` packs are named) passes `validate.mjs` and plays all its items, then fails the playthrough with "2 items drawn, 0 expected from the draw entries" and "the last attempt keeps drawn [...]". Every coding-int, research-int and systems mock built on prefix packs would fail `--exams`. Fix: copy the engine's test into `poolOf`: `|| String(d.id).startsWith(name + '-')`. Also make `poolOf` honour the shared `used` set across entries (finding 7) so `want` matches.

2. **error** | `app/tools/playthrough.mjs` 908 (and 506) | `--bank` reads `it.widget.kind` for every item. A bank item with `parts` has no widget, so `node tools/playthrough.mjs --bank <file>` throws "Cannot read properties of undefined (reading 'kind')" and marks the item failed (reproduced with a scratch bank file that the validator accepts with 0 errors). Beyond the crash, the loop answers one part and continues, so a bank deck with a parts item has never been played end to end by any test: neither the samples nor the real bank holds one. Line 506 (`p.widget.kind`) has the same shape for any part with no widget. Fix: use `(it.widget || (it.parts && it.parts[0].widget) || {}).kind`, and when `c.part != null && c.part < c.parts - 1` answer, check and continue until the last part. Add one `parts` item to `bank/sample-draw.json` so the deck path is exercised.

3. **error** | `app/tools/validate.mjs` 1305-1310 (with `checkItem` returning `'parts'` at 1101) | The homework rules "at least one `code` item" (programming courses) and "at least one `order` or `expression` item" read the item kinds, and an item with parts reports the kind `'parts'`. Scenario: coding-int level 4 homework puts its code in follow-up parts of live-round items (the reason C-parts-code exists). If that homework has no standalone `code` item, `validate.mjs` reports "homework in a programming course needs at least one code item" although code is set. The same applies to a maths homework whose only `expression` is a part. Fix: where kinds are collected, return `['parts', ...part widget kinds]` or add each part's widget kind to `kinds`; keep `longform` refused as a part so that rule is unchanged.

### Warnings

4. **warning** | `app/js/engine/mock.js` 106-107 and `app/tools/validate.mjs` 1857 (`drillTags`) | A drill's item tags are its `tags` or, only when there are none, its `pattern`. A drill with `tags: ["two-sum"]` and `pattern: "hashing"` therefore has the family `two-sum` and does not match `draw: { "from": "drills/ci", "tags": ["hashing"] }`. The coding-int brief (line 46) and AUTHORING's own draw example filter by the pattern vocabulary. The validator mirrors the engine, so an author sees "draws 2 but only 0 items match" rather than a silent mismatch, but the fix is then to drop `tags` from the drill, which loses the family balance. Fix: make the item's tags `[...tags, pattern]` (deduplicated, tags first so the family is unchanged) in both places, and say so in AUTHORING's "Sources" bullet.

5. **warning** | `app/js/engine/player.js` 1121-1129 (`widgetOf`) and `validate.mjs` 1155-1158 | Cumulative tests gather every earlier code part's own `tests`, whether or not that part is itself `cumulative: false`. Scenario: part 2 sets `cumulative: false` because it changes part 1's behaviour; part 3 (cumulative by default) then runs part 1's tests, which a correct part-3 answer built on part 2 fails, and the author is told only "the cumulative tests come to n". Fix: when an earlier part has `cumulative: false`, start the merge from that part (drop everything before it), and say so in AUTHORING "Code parts". Also note there that tests which rely on an earlier part's `setup`, `prelude`, `postlude`, `files` or `data` run under the later part's widget, so each code part must carry those fields itself.

6. **warning** | `app/js/engine/mock.js` 110 (`drillItem`) | `drillItem` copies `d.difficulty || 3` and uses the drill's `starter`, but a Python drill's own `fn`, `returns` and typed-result check (`__zq_typed` in `drill.js` 52-62, which requires the result to have the expected type, for example a `Fraction` for `compare: "fraction"`) are not applied: the drawn item is graded by the `code` widget's `isclose`/`equal`, so a drill whose tests are written for the stricter drill harness can accept an answer in an exam that the drill page refuses. Not seen in the eight real drills (all pass), but the sample drills do not exercise it. Fix: state it in AUTHORING "Code" under Drawn items ("a drawn drill is graded by the code widget, not the drill harness"), or run the type check through `widget.tests[*].compare`.

7. **warning** | `app/js/engine/mock.js` 142-153 and `validate.mjs` 1859-1880 | `used` is shared across a paper's entries, but `verifyDraws` checks each entry's pool on its own. Scratch mock: `draw: [{ "from": "drills/*", "n": 7 }, { "from": "drills/sharpe", "n": 1 }]` validates with a warning only, then each attempt holds 7 items, not 8, because the 8 real drills were already taken by the first entry (the engine writes a `console.warn`, nothing the learner sees). `passNet`, `pass` and "most the paper can give" are computed from the short paper, so a pass mark set for 8 items becomes easier. Fix: in `verifyDraws`, subtract items claimed by earlier entries of the same paper (or error when two entries' pools overlap and the sum of `n` exceeds the union), and make the engine fill a short entry from the same pool's unused items where it can.

8. **warning** | `app/js/engine/mock.js` 157-161 (`seenOf`), `docs/AUTHORING.md` "Fresh and balanced" | AUTHORING says `#exam/<id>/<seed>` fixes the draw "as for generated items". Once an attempt exists, `seen` changes and the same seed draws different items, so the URL is not a stable reproduction of a drawn paper, and the playthrough's two draws at seed 777 agree only because its state is empty. Fix: either say in AUTHORING that the seed fixes the draw only for a learner with no earlier attempts, or store `seen` snapshots with the attempt and pass the earliest one when a seed is given.

9. **warning** | `docs/AUTHORING.md` 548 ("Sources") against 5 "Drill" bullet | The "Sources" bullet says `drills/<pack>` is a drill whose `pack` is `<pack>` or whose id is `<pack>`; the Drill bullet, the engine, the validator and the playthrough (after fix 1) also match the id prefix `<pack>-`. An author reading only the draw section names a prefix pack and finds `drills/ci` matches nothing, or reads "matches nothing" as the rule. Fix: one sentence in each place, the same: pack field, id, or id prefix `<pack>-`.

10. **warning** | `docs/AUTHORING.md` 437 (canvas table), `app/js/engine/canvas/README-B.md` 735-736 | The AUTHORING `interleave` row lists the step ops but not the per-op fields (`reg`, `var`, `lock`, `by`, `value`, `text`, `ops`), and not that `wait` takes an optional `lock` which it frees and does not take again on waking, which is the one rule a mutex-and-condition-variable lesson (systems l10) will trip on: write `wait` with `lock: "m"` then a `lock` step, or mutual exclusion silently ends at the wake. Only README-B has the op table. Fix: copy the op table (or a two-line version with the `wait` rule) into AUTHORING section 4.

11. **warning** | `docs/AUTHORING.md` 554-556 ("Samples") | The sample list omits `exams/mock-sample-data.json`, `exams/mock-interleave-sample.json`, `drills/sessions/sample-session.json` and `content/data/sample-prices.csv`.
