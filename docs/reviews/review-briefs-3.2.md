## [Must] engine requirements

1. **P32-expr-exp** (blocks ito level 2 l6, ito level 4 l16, measure-prob level 4 l14, l15 and l16). The `expression` grader does not read `\exp`. Compute Engine 0.30.2 parses `\exp(x)` as the tuple `["Tuple", "Exp", "x"]`, so `\exp(x)`, `\exp\left(x\right)` and `\exp x` are all marked wrong against an authored `e^{x}` (and `\exp(W)` against `e^{W}`), and the reverse. MathLive's inline shortcut turns the typed letters "exp" into `\exp` (`mathlive.js`, `INLINE_SHORTCUTS`), so this is the natural way for a learner to write the answers these screens ask for: the Girsanov density `e^{-\theta w - \theta^2 t/2}`, the weights `e^{\theta x - \theta^2/2}` and `e^{-\theta x + \theta^2/2}`, `d(e^W)`, and the power payoff `S_0^n e^{n(r-\sigma^2/2)T + n^2\sigma^2T/2}`. An `accept` list cannot cover it, because each `\exp` form must then be listed with every rearrangement of its argument. Spec: in `prep()` of `app/js/engine/grade.js`, before parsing and on both sides of `exprEqual` (and in `exprEqualUpToConstant`), rewrite `\exp`, `\operatorname{exp}` and `\mathrm{exp}` followed by a bracketed argument (`(...)`, `\left(...\right)`, `{...}`) or one token into `\exponentialE^{(argument)}`. Regression cases that must pass: `\exp(x)` with `e^{x}`, `\exp\left(\theta x-\frac{\theta^2}{2}\right)` with `e^{\theta x-\theta^2/2}`, `S_0\exp(\sigma W_T)` with `S_0e^{\sigma W_T}`, and `\exp(W)` with `\exp(W)`. Add a validator warning for an authored `answer` or `accept` that contains `\exp`.

2. **P32-expr-callhead** (blocks ito level 4 l16; any answer a learner may type as a letter followed by a bracketed sum). Compute Engine reads a letter or Greek letter directly before `(` as a function call, and declares the symbol as a function in the one engine the page shares. In the widget's order (input first, target second): `r(1-x)` against `r-rx` fails, `r(1-x)` against `r\cdot(1-x)` fails, `K(v_x-v_y)` against `Kv_x-Kv_y` fails, `\sigma(S+1)` against `\sigma S+\sigma` fails, and `k(1-r)` against `k\cdot(1-r)` fails; the same two forms pass in the other order. After `x(y+1)` is the first expression a page parses, `2x` against `x+x` and `x^2` against `x\cdot x` also fail on that page until it reloads (reproduced with one shared engine). For the topic this hits the power payoff follow-up, whose exponent is `n(r-\sigma^2/2)T`: a learner who writes `n(r-0.5\sigma^2)T` is marked wrong, and so is every later screen that uses `n` as a number. No authoring convention fixes it, because the failing form is the learner's. Spec: in `prep()` insert `\cdot` between a lone Latin or Greek letter (with an optional subscript or superscript) and an immediately following `(` or `\left(`, unless the letter is listed as a function by the screen (a new optional `functions: ["f"]` on the expression widget); and run each `exprEqual` in a scope where every unknown is declared a real number (`ce.declare(name, 'real')`) or a fresh engine, so one parse cannot change what a symbol means on the next screen. Regression cases: the five above, then `2x` against `x+x` after them on one page.
